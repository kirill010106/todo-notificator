# ToDo Notificator

Монорепозиторий для управления задачами с email-напоминаниями, Pomodoro, JWT-аутентификацией и геймификацией.

## Возможности

- Задачи и категории: создание, изменение, удаление, массовое завершение и удаление задач.
- Фильтрация задач по статусу и категории, поиск по заголовку/описанию, сортировка и пагинация.
- Pomodoro с привязкой к задаче или свободной сессией, перерывами и завершением/отменой.
- Профиль, XP, уровни, серии активности, достижения и ежедневные задания.
- Автовход после регистрации, необязательное отображаемое имя, смена email/пароля и восстановление забытого пароля.
- Подтверждение email включает уведомления; пользоваться приложением можно сразу. Access/refresh tokens и выход со всех устройств.
- Email-напоминания через SMTP: webhook пересчитывает расписание, polling служит резервным механизмом.
- История активности через отдельный gRPC-сервис с MongoDB.
- Премиум через YooKassa: создание платежа, webhook и сверка ожидающих платежей.
- Метрики Prometheus и конфигурация Grafana.

В бесплатном тарифе доступны до 3 категорий, до 2 напоминаний на каждую задачу и последние 5 записей истории. Общего лимита напоминаний аккаунта нет. Premium снимает тарифный лимит напоминаний: `reminders_per_task_limit=null` (Free: `2`); для категорий безлимит обозначается `-1`. Актуальные тариф и подтверждение email проверяются по БД.

## Структура

```text
backend/           REST API: Go, chi, pgx, goose; SQL-миграции и тесты
frontend/          React + TypeScript + Vite: задачи, фокус, прогресс и награды
activity-logger/   gRPC-сервис истории активности с MongoDB
notifiers/email/   SMTP-уведомления и прием webhook от backend
notifiers/shared/  Модели, PostgreSQL-хранилище и планировщик уведомлений
notifiers/telegram-bot/  Заготовка Telegram-бота, не входит в dev.ps1 и Compose
proto/             Контракт gRPC activity-logger
pkg/               Сгенерированный Go-код gRPC
scripts/loadtest/  Нагрузочный сценарий пользователей и задач
docs/             Swagger UI и OpenAPI (openapi.yaml)
deploy/            Настройки Grafana
ansible/           Развертывание
```

Go-модули объединены в `go.work`. React-клиент находится в `frontend/`.

## API

Базовый префикс: `/api/v1`. Полный контракт с телами запросов, ответами и ошибками: [docs/openapi.yaml](docs/openapi.yaml). Источником маршрутов служит `backend/internal/http-server/router/router.go`.

| Доступ | Методы и пути относительно `/api/v1` |
| --- | --- |
| Публичный | `POST /register`, `POST /login`, `POST /refresh`, `POST /password/forgot`, `POST /password/reset`, `GET /verify?token=...`, `GET /health`, `GET /` |
| Webhook YooKassa, без JWT, с проверкой IP | `POST /webhooks/yookassa` |
| Авторизация, Bearer JWT | `POST /logout`, `POST /verify/resend`, `POST /me/email`, `POST /me/password` |
| Начальное состояние и профиль, Bearer JWT | `GET /me/bootstrap`, `GET /me/profile`, `PATCH /me/profile`, `GET /me/achievements`, `GET /me/quests` |
| Магазин, Bearer JWT | `GET /me/shop`, `POST /me/shop/actions` |
| План дня, фокус и награды, Bearer JWT | `GET /me/today`, `GET /me/focus`, `POST /me/focus/resume`, `POST /me/focus/rest/finish`, `POST /me/quests/{code}/claim`, `POST /me/rewards/daily-chest/claim` |
| Статистика и история, Bearer JWT | `GET /me/stats`, `GET /me/logs` |
| Задачи, Bearer JWT | `GET /tasks`, `POST /tasks`, `PATCH /tasks/{task_id}`, `DELETE /tasks/{task_id}`, `POST /tasks/bulk-complete`, `POST /tasks/bulk-delete` |
| Категории, Bearer JWT | `GET /categories`, `POST /categories`, `GET /categories/{category_id}`, `PATCH /categories/{category_id}`, `DELETE /categories/{category_id}` |
| Pomodoro, Bearer JWT | `GET /pomodoros/active`, `POST /pomodoros/start`, `POST /pomodoros/{id}/pause`, `POST /pomodoros/{id}/stop` |
| Платежи, Bearer JWT | `POST /payments/create`, `POST /payments/sync` |
| Только `ENV=local`, Bearer JWT | `POST /dev/toggle-premium` |

Вне префикса API доступны `GET /` (информация о сервисе) и `GET /ping` (ответ `pong` без проверки БД). `GET /api/v1/health` проверяет доступность PostgreSQL. Метрики находятся на отдельном HTTP-сервере: локально `http://localhost:9091/metrics`.

Для защищенных методов передавайте `Authorization: Bearer <access_token>`. В локальном конфиге access token действует 15 минут, refresh token — 168 часов. Актуальные Premium и подтверждение email проверяются по БД. Общий лимит HTTP-сервера: 100 запросов в минуту на IP; превышение возвращает JSON `429` с `Retry-After`.

`GET /tasks` принимает `limit` (по умолчанию 20, значения выше 100 ограничиваются до 100), `offset` (по умолчанию 0), `status` (`all`, `pending`, `done`, `burnt`), `search`, `category_id`, `sort_by` (`created_at`, `deadline`) и `order` (`asc`, `desc`). По умолчанию задачи сортируются по дате создания убывающе; при `sort_by=deadline` — по дедлайну возрастающе, без даты в конце. Для изменения направления передавайте и `sort_by`, и `order`.

`GET /me/bootstrap` возвращает пользователя с лимитами и `timezone`, категории, первые 20 задач, статистику, геймификацию и `focus` с серверным временем и сохраненными перерывами. Поле `active_pomodoro` сохранено для совместимости. При ошибке загрузки фокуса сервер возвращает ошибку, а не состояние ожидания.

Ошибки содержат `code`, `message`, `request_id`, `field_errors`; прежнее поле `error` сохранено для совместимости. Webhook YooKassa при успехе возвращает пустой `200`, а ряд ошибок — `text/plain`.

`PATCH /tasks/{task_id}` принимает явный `null` для снятия срока и категории; отсутствующие поля сохраняются. Напоминания передаются массивом `reminders`: пропуск сохраняет настройки, `[]` удаляет. Время отправки рассчитывается из `deadline` и произвольного `offset_minutes`; старые поля `reminder_at` и `is_notified` отклоняются. [Модель, перенос данных и доставка](docs/REMINDERS.md). `GET /tasks` также принимает `deadline_from` (включительно), `deadline_before` (исключительно), `has_deadline`. `GET /me/today` возвращает отдельные страницы и полные счетчики групп: просроченные до серверного текущего времени и оставшиеся сроки до конца дня в часовом поясе профиля. Изменить пояс можно через `PATCH /me/profile` с `timezone` IANA, по умолчанию UTC.

Создание/редактирование задач, массовое завершение, команды Pomodoro и получение дневных наград поддерживают `Idempotency-Key` (до 128 символов). Ключ хранится в пределах аккаунта вместе с успешным ответом в одной транзакции. Повтор того же запроса возвращает прежний результат; другое действие с тем же ключом — `409`. Ответы этих команд дополнены `operation_id`, `result`, `rewards`, `stats`, `unlocked_achievements` и `focus`. Сохраняйте ключ при повторе после потери ответа. Подробная схема — в Swagger.

## Аккаунт и восстановление доступа

Регистрация принимает необязательное `display_name` и сразу возвращает пару токенов для входа. Имя (до 80 символов после обрезки пробелов) можно менять через `PATCH /me/profile`; пустая строка очищает его. `timezone` и имя изменяются независимо.

`POST /me/email` (`email`, `current_password`) сразу меняет логин и приостанавливает email-уведомления до подтверждения нового адреса. `POST /me/password` (`current_password`, `new_password`) меняет пароль. Оба метода возвращают новую пару токенов для текущего браузера и отзывают прежние сессии. Передача прежнего email возвращает `changed=false` без смены токенов. Пароли: минимум 8 символов, максимум 72 байта UTF-8.

`POST /password/forgot` (`email`) всегда отвечает одинаковым `202` для корректного адреса. Письмо восстановления доступно и без подтверждённой почты; лимит — одно письмо в минуту и пять в час на адрес. Ссылка из настроенного `app_url` ведёт на `/reset-password?token=…`, действует 30 минут и заменяется новым запросом. `POST /password/reset` (`token`, `new_password`) атомарно меняет пароль и завершает все сессии; затем пользователь входит заново. Восстановление не подтверждает email. Смена почты аннулирует прежние ссылки обоих типов.

Миграция `00025_account_security.sql` добавляет имя, версию авторизации, адрес в ссылках подтверждения и отдельную очередь восстановления. JWT без версии совместимы с версией аккаунта `0`. SMTP обслуживает существующий email-сервис с повторами; в таблице восстановления хранится SHA-256 токена, исходный токен очищается из очереди после отправки или отмены. Порядок выпуска: миграция, backend и email-worker, frontend.

## Статистика, награды и удаление

Статистику рассчитывает сервер. Публичного `PATCH /me/stats` нет: такой запрос получает `405`. Результат действия содержит обновленные значения; отдельно доступны `GET /me/stats` и `GET /me/bootstrap`.

- Первое завершение задачи дает 10 очков. Повторное открытие и завершение не дублируют награду.
- Засчитанный Pomodoro дает 20 очков; если одновременно впервые завершена задача — еще 10. Достижения могут добавить бонусы.
- Порог засчитывания сессии — 24 минуты по времени БД для таймера на 25 минут. Короткая сессия не дает награды за Pomodoro; явное завершение задачи все равно может дать ее обычные 10 очков.
- Массовое завершение использует те же правила. Изменения задач, награды и достижения сохраняются в одной транзакции; ошибки записи откатывают всю операцию.
- Повторная остановка завершенной сессии без прежнего ключа возвращает `404`; с тем же ключом — сохраненный успех. Запуск с чужой или несуществующей задачей возвращает `404`.
- Бонусы достижений и дневных заданий не продлевают стрик. Получение награды задания и дневного сундука защищено уникальностью аккаунт/день/код. Размер XP задает сервер; сундук дает 50 XP за выполнение всех заданий. Прогресс сохраняется при удалении задачи; повторное сохранение выполненной задачи не добавляет завершений.
- Удаление категории сохраняет задачи без категории. Удаление задачи завершает активный таймер без штрафа и сохраняет историю сессий без ссылки на задачу. Массовое удаление действует аналогично.

В первые 30 секунд сессию можно отменить через `POST /pomodoros/{id}/cancel` без штрафа и изменения задачи. При ручном прерывании сессии с задачей сохраняется штраф 30 очков; свободная сессия прерывается без штрафа и остается в истории. Уровень пересчитывается из очков. Подробные правила и транзакционные гарантии: [docs/BUSINESS-LOGIC.md](docs/BUSINESS-LOGIC.md).

В локальном конфиге backend применяет миграции при запуске (`auto_migrate: true`). В production он только проверяет схему; перенос выполняет отдельный шаг безопасного выпуска. См. [DEPLOYMENT.md](docs/DEPLOYMENT.md). `00018` задает правила удаления, `00019` добавляет состояние фокуса, часовой пояс, идемпотентные операции и дневные награды, `00020` — журнал дневных действий над задачами. Перед обновлением сохраните резервную копию БД; новый клиент требует обновленного backend. Миграция `00021` переносит напоминания; перед запуском обязательно остановить старый email-планировщик и следовать [порядку обновления](docs/REMINDERS.md).

Миграция `00022` добавляет серверный магазин: начальный баланс 50 монет, +5 за первое завершение задачи, +10 за засчитанный фокус. Покупки и начисления атомарны. Бустер за 100 монет даёт 40 XP вместо 20 за следующую засчитанную сессию; ранняя отмена его не расходует. Старые личные награды и настройки импортируются один раз, браузерный баланс не переносится. Подробнее: [frontend и магазин](docs/FRONTEND.md).

## Требования

- Go 1.26+ для работы с текущим `go.work` и корневым модулем.
- Node.js 24 и npm для сборки фронтенда и Swagger UI.
- PostgreSQL (в локальном скрипте используется `16-alpine`).
- MongoDB для истории активности (в локальном скрипте используется MongoDB 7).
- Docker Desktop и PowerShell для `dev.ps1`; Air для перезапуска сервисов при изменениях.

## Локальный запуск

Все команды ниже выполняются из корня репозитория, если не указано иначе.

### 1. Один корневой .env

```powershell
Copy-Item .env.example .env
```

Не перезаписывайте существующий `.env`: перенесите недостающие параметры из шаблона. Backend, email, activity-logger и Telegram-заготовка используют один файл в корне. Вложенные `.env` не читаются. Заполните SMTP и секреты; локальный адрес PostgreSQL по умолчанию — `127.0.0.1:5433/todo`, MongoDB — `127.0.0.1:27017`.

Относительные `CONFIG_PATH=backend/config/local.yaml` и `EMAIL_CONFIG_PATH=notifiers/email/config/local.yaml` разрешаются от корня проекта, независимо от текущей папки. Для запуска из другой директории можно передать абсолютный `ENV_FILE`; пути YAML тогда разрешаются от каталога выбранного файла. Переменные процесса имеют приоритет. В контейнерах `.env` не копируется: Compose передаёт настройки окружением и задаёт абсолютные пути `/app/config/prod.yaml`.

После изменения `.env` перезапустите процессы сервисов целиком. Air не отслеживает этот файл. Правила загрузки и проверка перехода: [ENVIRONMENT.md](docs/ENVIRONMENT.md).

Локальные YAML-конфиги находятся в `backend/config/local.yaml` и `notifiers/email/config/local.yaml`. Backend слушает `8082`, email webhook — `8084`, activity-logger — `50051`, метрики — `9091`.

### 2. Запуск через dev.ps1

Установите Air, если его нет в `PATH`:

```powershell
go install github.com/air-verse/air@latest
```

Запустите Docker Desktop, затем:

```powershell
./dev.ps1
```

Скрипт создает или запускает PostgreSQL (`todo-local-pg-alt`, порт `5433`) и MongoDB (`todo-mongodb`, порт `27017`), ждет готовности, открывает три PowerShell-окна с Air (backend, email и activity-logger) и запускает frontend через Vite на `http://127.0.0.1:3030`. Перед первым запуском установите зависимости: `npm --prefix frontend ci`. Изменения интерфейса подхватываются автоматически; журналы Vite находятся в `tmp/frontend/vite.log` и `tmp/frontend/vite-error.log`. При Ctrl+C фронтенд останавливается вместе с сервисами. Если frontend запущен отдельно или нужен только backend, используйте `./dev.ps1 -SkipFrontend`; этот флаг можно сочетать с `-SkipDatabases`. Порт frontend фиксирован: если `3030` занят, Vite завершится с ошибкой вместо перехода на другой порт. Все настройки сервисов берутся из корневого `.env`; скрипт передаёт только абсолютный `ENV_FILE`. Он подготавливает базы со стандартными локальными портами; для своих баз используйте `./dev.ps1 -SkipDatabases`. Скрипт завершает ранее запущенные процессы `app` этого проекта. При остановке сервисов контейнеры БД остаются запущенными.

Если Docker Desktop ещё запускается, скрипт ожидает готовности Engine. При ошибке `500 Internal Server Error` контейнеры не пересоздаются: дождитесь готовности Docker Desktop, при повторении ошибки перезапустите его и снова выполните `./dev.ps1`. Скрипт сохранён в UTF-8 с BOM для корректного отображения кириллицы в Windows PowerShell 5.1.

### 3. Альтернатива: ручной запуск

Для тех же локальных портов создайте базы:

```powershell
docker run --name todo-local-pg-alt -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=todo -p 127.0.0.1:5433:5432 -d postgres:16-alpine
docker run --name todo-mongodb -p 127.0.0.1:27017:27017 -d mongo:7
```

Если эти контейнеры уже созданы, используйте `docker start todo-local-pg-alt todo-mongodb`.

Эти учетные данные предназначены только для локальной разработки. Команды выше
и `dev.ps1` ограничивают доступ новых контейнеров loopback-адресом. Запуск существующего контейнера не
меняет его привязки портов. Не используйте демонстрационный пароль для внешней БД;
не пересоздавайте контейнер с нужными данными без резервной копии и плана переноса.

Запустите каждый сервис в отдельном терминале из корня проекта:

```powershell
# Терминал 1
Set-Location activity-logger
go run ./cmd/main.go
```

```powershell
# Терминал 2
Set-Location backend
go run ./cmd/main.go
```

```powershell
# Терминал 3
Set-Location notifiers/email
go run ./cmd/main.go
```

Локально backend автоматически применяет встроенные SQL-миграции; в production отдельный шаг выпуска переносит БД, а backend проверяет её версию. Регистрация и повторная отправка подтверждения сохраняют письмо в PostgreSQL outbox вместе с токеном. Недоступность SMTP не отменяет успешный ответ: email-worker отправит письмо позднее, до пяти попыток. Старая ссылка, созданная до появления outbox, не ставится в очередь автоматически; используйте `/verify/resend`. Недоступный activity-logger не останавливает основной API; `/me/logs` возвращает `503`, если клиент не инициализирован, либо `500` при ошибке обращения к сервису.

### 4. Веб-клиент

Из корня проекта:

```powershell
Set-Location frontend
npm ci
npm run dev
```

Откройте [http://127.0.0.1:3030](http://127.0.0.1:3030). Vite перенаправляет `/api` на `127.0.0.1:8082`. Ссылки из писем и оплаты используют `APP_URL` и `CLIENT_URL`; используйте одно имя хоста для сохранения браузерной сессии. При необходимости задайте полный адрес API с `/api/v1` в корневом `.env`: `VITE_API_BASE_URL=http://localhost:8082/api/v1`.

Для production выполните `npm run build`; результат — `frontend/dist/`. Dockerfile собирает приложение и раздаёт его через Nginx с поддержкой внутренних маршрутов. Аргумент сборки `VITE_API_BASE_URL` по умолчанию равен `https://todoapi.chkpnk.ru/api/v1`. Шрифт Manrope с кириллицей включён в сборку; внешние CDN для интерфейса не нужны.

Новый клиент включает «Сегодня», задачи, категории, Pomodoro, прогресс, достижения, историю, аккаунт, оплату и локальные награды. Монеты и инвентарь разделены по аккаунтам; старые общие данные браузера однократно получает первый вошедший аккаунт, исходные ключи сохраняются. Бустеры без серверного эффекта недоступны для покупки. Особенности текущего API и предложения развития: [docs/FRONTEND.md](docs/FRONTEND.md).

### 5. Swagger UI

```powershell
Set-Location docs
npm ci
node server.js
```

Откройте [http://localhost:8080](http://localhost:8080). Выберите сервер `Local backend` для локальных запросов. Для защищенных методов выполните `/login`, затем вставьте `access_token` в поле **Authorize**.

## Платежи и развертывание

Для серверного окружения есть отдельный шаблон `.env.production.example`. В отдельном checkout заполните его и сохраните как `.env`, затем выполните `python scripts/deploy_release.py --root . --backups .local-backups --check`. Это проверка конфигурации без запуска и остановки контейнеров. `IMAGE_BASE` и единый SHA в `IMAGE_TAG` обязательны; `TRUSTED_PROXIES` автоматически определяется при выпуске на сервере; локальный `.env` не заменяет production-настройки. Локально SMTP меняется в корневом `.env` с полным перезапуском email-процесса; основной Compose предназначен для сервера.

Интеграция YooKassa включается при заданных `SHOP_ID` и `SECRET_KEY` в окружении backend. Без них `/payments/create` и webhook возвращают `503`, `/payments/sync` оставляет ожидающие платежи pending. Сумма сейчас задана в обработчике: `49.00 RUB` за Премиум навсегда. Backend формирует URL возврата из `CLIENT_URL`; webhook провайдера должен указывать на `/api/v1/webhooks/yookassa`. Доступ к webhook ограничен IP YooKassa и loopback. Локально тариф можно переключить через `/dev/toggle-premium`; новый тариф проверяется по БД без обновления JWT.

`docker-compose.yml` предназначен для развертывания с готовыми образами `${IMAGE_BASE}-backend`, `${IMAGE_BASE}-email`, `${IMAGE_BASE}-activity-logger`, `${IMAGE_BASE}-frontend`, PostgreSQL на том же сервере с именованным томом и внешней сетью Traefik `traefik`. В production задайте `POSTGRES_PASSWORD` (имена `POSTGRES_USER` и `POSTGRES_DB` по умолчанию `todo`); строку подключения Compose соберёт сам. Явный `DATABASE_URL` позволяет использовать внешнюю БД вместо встроенной. Это не локальный Compose с секциями `build`. Он запускает MongoDB, сервисы приложения, Prometheus (`9090`) и Grafana (`3001`); backend и frontend публикуются через Traefik. Backend и email используют корневой `.env` и конфиги `prod.yaml`. Настройки деплоя также находятся в `ansible/`, `prometheus.yml` и `deploy/grafana/`. Для обновлений использовать [сценарий безопасного выпуска](docs/DEPLOYMENT.md): обязателен единый `IMAGE_TAG` (SHA); адрес Traefik определяется автоматически. Прямой `compose up` не выполняет безопасный перенос.

## Тестирование

Полный backend-набор включает PostgreSQL-интеграцию и проверку гонок в CI.
Минимальное совместное покрытие рабочего кода `backend/` — 80%; отчёт сохраняется
как артефакт `backend-coverage`. Команды запуска и состав проверок:
[docs/BACKEND-TESTING.md](docs/BACKEND-TESTING.md).

Проверки фронтенда:

```powershell
Set-Location frontend
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Браузерные тесты используют фикстуры текущего API, автоматически запускают Vite и проверяют размеры 360, 768 и 1440 px. Это проверка клиента; реальная доставка писем и платёжная система требуют отдельной проверки с настроенным backend.

Обычные тесты запускаются отдельно в каждом Go-модуле:

```powershell
Set-Location backend
go test ./... -count=1
Set-Location ../activity-logger
go test ./... -count=1
Set-Location ../notifiers
go test ./... -count=1
Set-Location email
go test ./... -count=1
```

Интеграционные проверки бизнес-логики и удаления запускаются на одноразовых PostgreSQL-контейнерах; требуется Docker:

```powershell
Set-Location backend
go test -count=1 -p 1 -tags integration ./internal/storage/postgres ./internal/http-server/router -run 'Test(FrontendContracts|BusinessActions|DeletionRelationships|APIContracts)$' -v
```

Проверяются параллельные и повторные запросы, выдача наград, владение задачами и сессиями, сохранение истории и откат при ошибке записи статистики. При нехватке памяти используйте `go test -p 1 ./...` для последовательной сборки пакетов.

E2E backend используют build tag `e2e` и testcontainers; требуется работающий Docker:

```powershell
Set-Location backend
go test -tags=e2e ./tests/e2e -count=1 -v
```

Вместо контейнера можно передать DSN отдельной тестовой PostgreSQL:

```powershell
$env:E2E_POSTGRES_DSN = 'postgres://postgres:postgres@localhost:5433/todo_e2e?sslmode=disable'
go test -tags=e2e ./tests/e2e -count=1 -v
```

Сценарий нагрузки запускается из корня и создает пользователей и задачи в указанном API; используйте тестовое окружение:

```powershell
go run ./scripts/loadtest -url http://localhost:8082 -c 10 -d 20s
```

## Текущее состояние и ограничения

Карта архитектуры: [.github/CODEBASE.md](.github/CODEBASE.md).
Актуальные статусы прежних замечаний, открытые риски и планы:
[docs/ROADMAP-ADVANCED.md](docs/ROADMAP-ADVANCED.md).

- Монеты, инвентарь и личные награды хранятся на сервере. Новый кошелёк получает 50 монет; локальный баланс не переносится, импортируются личные награды и настройки.
- Напоминания используют аренду задания между работниками и до пяти попыток SMTP.
  Сбой после принятия письма SMTP до записи успеха может привести к повтору; журнал
  активности доставляется best-effort.
- Выдача Premium и статус платежа сохраняются атомарно. Создание внешнего платежа
  и запись в БД — разные операции: повтор с тем же клиентским ключом использует
  тот же ключ YooKassa и повторяемую запись платежа. При ошибке повторяйте ту же попытку.
- Метрики и автоматические тесты уже есть. Реальную доставку SMTP, оплату и полный
  цикл фокуса следует проверять отдельно; тесты с фикстурами этого не подтверждают.
