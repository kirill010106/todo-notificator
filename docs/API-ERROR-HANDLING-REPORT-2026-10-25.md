# Обработка ошибок HTTP API: отчёт и план изменений

Дата: 25 октября 2026 года. База анализа: HEAD `6c32fb8` и текущие исходники рабочей копии.

Статус исходного отчёта: при его подготовке создан только этот документ. Впоследствии выполнены этапы 0–4: baseline, общий рендерер, миграция источников, инфраструктурные ответы, согласование контракта и удаление глобального нормализатора. Подробный анализ ниже описывает исходное состояние; актуальный результат приведён в отчётах этапов.

## Вывод

Исходный анализ показал необходимость единого способа формирования ошибок. На момент анализа совместимость HTTP-контракта во многом обеспечивал глобальный middleware, который перехватывал записанный ответ, разбирал его и добавлял недостающие поля. Обработчики при этом возвращали разные структуры.

Главная проблема — стоимость сопровождения и зависимость поведения клиента от текста сообщения. Дополнительная буферизация ответов подтверждается исходниками, но её влияние на задержки и память не измерялось. Этот отчёт не доказывает существенное замедление или отказ сервера.

Предлагаемый результат: обработчик или middleware сразу передаёт явные статус, код, безопасное сообщение и ошибки полей единому HTTP-рендереру. Глобальное исправление тела ответа постепенно удаляется после перевода всех источников ошибок.

Материалы нулевого этапа: [матрица текущих ответов и регрессионные проверки](API-ERROR-BASELINE-2026-10-25.md). В ней отдельно приведены результаты исполнения; ниже сохранены исходные анализ и план.

Материалы первого этапа: [общий рендерер, защита изменений и проверка согласованности](API-ERROR-RENDERER-2026-10-25.md).

Материалы второго этапа: [миграция источников ошибок, защита файлов и проверки без нормализатора](API-ERROR-MIGRATION-2026-10-25.md).

## 1. Что проверено

Проверены подключение маршрутов и порядок middleware в [router.go](../backend/internal/http-server/router/router.go), основные способы формирования ошибок, исполнитель идемпотентных команд, OpenAPI и потребители ошибок во frontend.

Метод проверки — чтение исходников, поиск вызовов и сопоставление с существующими тестами. HTTP-сценарии и тестовые наборы в рамках подготовки отчёта не запускались. Выводы о выполнении запросов ниже основаны на прослеженной цепочке вызовов; измерений производительности нет.

Публичная регистрация проверялась через актуальный `account.Handler.Register`. Старый `handlers/auth/register.New` не использован как основание для выводов о действующем API.

## 2. Подтверждённые проблемы

### 2.1. Машинный код зависит от текста сообщения

Место: [middleware/contracts/contracts.go](../backend/internal/http-server/middleware/contracts/contracts.go), `defaultCode`, строка 126.

Если обработчик не передал `code`, middleware ищет фрагменты сообщения. Для исчерпанного перерыва это `extra break is already used`, для лимита категорий — `не более 3 категорий`.

Цепочка подтверждена на подключённых маршрутах:

- `POST /categories`: [create.go](../backend/internal/http-server/handlers/categories/create/create.go), строка 91, распознаёт `storage.ErrCategoryLimitReached` и возвращает текст через `resp.Error`. Код `CATEGORY_LIMIT_REACHED` появляется позже, после поиска подстроки.
- `POST /pomodoros/{id}/pause`: [pause.go](../backend/internal/http-server/handlers/pomodoros/pause/pause.go), строка 53, возвращает текст через `resp.Error`. Код `BREAK_ALREADY_USED` также назначается позже.

Последствие: при замене сообщения, например на «Можно создать до трёх категорий», специальный код перестанет определяться и для HTTP 403 получится общий `FORBIDDEN`. Frontend уже использует специальные коды для выбора сообщения. Это конкретная зависимость, которую следует устранить первой.

Изменение: назначать код в точке распознавания типизированной ошибки. Сообщение можно редактировать независимо от кода. Не заменять поиск подстроки сравнением полного текста: зависимость от формулировки при этом сохранится.

### 2.2. Единый внешний формат получается только после преобразования ответа

Места: генераторы из таблицы выше и `Errors`, строка 81.

Форма ошибки различается до выхода из обработчика. `request_id` добавляет внешний middleware; `validation_errors` копируются в `field_errors`; `error` и `message` приводятся к одному значению. Часть обработчиков явно пишет `field_errors`, часть полагается на добавление пустого объекта извне.

При этом явный `field_errors: null` не заменяется пустым объектом: middleware проверяет наличие ключа, а не тип значения. Такой JSON может получиться при сериализации `ContractError.Fields == nil` через `RenderContractError` или ветви `Operation`.

Последствие: единый контракт трудно обеспечить при добавлении нового обработчика или его отдельном тестировании. Наличие поля ещё не гарантирует ожидаемый тип. Это несогласованность формирования ответа, а не доказательство текущего сбоя интерфейса.

Изменение: собирать полный ответ в одном месте, включая `request_id` из контекста и нормализацию ошибок полей. Отдельно зафиксировать переход от `null` к `{}` как наблюдаемое уточнение контракта.

### 2.3. Весь ответ буферизуется ради нормализации ошибок

Место: `Errors`, строки 81–124.

Для запросов, чей путь не содержит `/webhooks/`, создаётся `httptest.ResponseRecorder`. В него записываются заголовки и тело. Затем результат копируется в настоящий `ResponseWriter`. Ошибочный JSON дополнительно разбирается и сериализуется.

Успешные ответы тоже проходят через этот буфер, хотя `Errors` не разбирает их JSON. Команды, обёрнутые в `Operation`, имеют ещё один recorder с отдельной задачей — исполнением обработчика внутри транзакции.

Последствие: дополнительная работа на каждом таком ответе и более сложный путь записи. Пока это вывод о механизме, а не численная оценка накладных расходов.

Изменение: после миграции источников ошибок удалить буферизацию именно из глобального `Errors`. Recorder в `Operation` оставить в рамках этой задачи: его удаление требует отдельного изменения исполнения команд.

### 2.4. Frontend компенсирует неоднородные ответы

Место: [frontend/src/lib/api.ts](../frontend/src/lib/api.ts), `errorText`, строка 254.

Клиент сначала использует `code`, затем HTTP-статус, затем проверяет язык и фрагменты сообщения. Есть отдельные регулярные выражения для старых англоязычных ответов. Сам HTTP-клиент также поддерживает `message` и прежний `error`.

Последствие: трактовка ошибок распределена между backend и frontend. Изменение текста на сервере может потребовать проверки клиентских эвристик.

Изменение: основным признаком оставить стабильный `code`, для неизвестного кода — безопасное сообщение и обработку HTTP-статуса. Совместимость со старыми ответами сохранять на время перехода, затем убирать только после миграции соответствующих источников.

### 2.5. OpenAPI отражает несколько вариантов ошибки

Место: [docs/openapi.yaml](openapi.yaml), схемы `ErrorResponse` и `APIError`, строки 45 и 404.

Основная схема использует строковый `status`, другая — числовой. `ErrorResponse` перечисляет общие поля, но не делает их обязательными. `APIError` применяется, в частности, к отсутствующему вне local методу `/dev/toggle-premium`.

Последствие: перенос всех ответов на один DTO с фиксированным строковым `status` изменит существующий контракт роутерных ошибок. Простая замена функций записи без проверки OpenAPI недостаточна.

Изменение: унифицировать механизм записи и общие поля, сохранив существующие варианты `status` на первом этапе. Их полное выравнивание оформить отдельным изменением контракта, если оно понадобится.

## 3. Целевая схема

### Общий HTTP-рендерер

Предлагается выделить пакет `backend/internal/http-server/apiresponse` как единственную реализацию записи JSON-ошибок прикладного API. Он отвечает за DTO ошибки, заголовок `Content-Type`, HTTP-статус, заполнение полей и получение идентификатора запроса из контекста.

Он не анализирует JSON, который уже записал другой обработчик, и не выводит код из текста. На переходном этапе существующие helpers могут делегировать запись в этот пакет; собственных реализаций сериализации в них оставаться не должно.

Существующую `resp.Response`, встроенную также в успешные ответы, не следует механически расширять обязательными полями ошибки: это может изменить JSON успешных операций. Для ошибки нужен отдельный DTO.

| Поле | Предлагаемое правило |
|---|---|
| HTTP-статус | Передаётся явно; сохраняет текущую семантику маршрута |
| `code` | Непустой стабильный код; не зависит от текста сообщения |
| `message` | Безопасное сообщение для клиента; внутренняя причина не сериализуется автоматически |
| `request_id` | Идентификатор текущего HTTP-запроса из middleware `RequestID` |
| `field_errors` | Объект строковых сообщений; при отсутствии ошибок полей — `{}` |
| `error` | Совместимый псевдоним `message`, сохраняется |
| `validation_errors` | Сохраняется у ответов, где уже присутствовал; содержит те же ошибки полей |
| `status` | Строковое или числовое значение согласно существующему семейству ответов |

Коды следует собрать в одном каталоге констант и документировать их назначение. Имена и значения уже используемых кодов сохраняются. Новые специальные коды вместо прежних общих требуют явного описания, даже если это улучшает точность сообщения.

### Распознавание ошибок

Ожидаемые ошибки распознаются через `errors.Is` и `errors.As`. Существующий `domain.ContractError` можно поддержать адаптером без изменения слоя хранения.

Общее преобразование допустимо для однозначных соответствий. Если один тип ошибки имеет разный смысл в разных сценариях, решение остаётся в соответствующем HTTP-адаптере. Например, отсутствие пользователя при входе не должно автоматически превращаться в ответ, раскрывающий наличие аккаунта.

Неизвестная внутренняя ошибка получает HTTP 500, `INTERNAL_ERROR` и безопасный текст. Диагностическая причина журналируется с `request_id` в выбранной точке обработки. Дублирующее журналирование одной причины следует исключить; тело запроса, токены и пароли в такую запись не включаются.

Разделение всех предметных ошибок и HTTP-статусов в domain не входит в этот этап. Оно не требуется для устранения текущих дублирующих рендереров.

## 4. Планируемые изменения и порядок перехода

| Этап | Изменения | Условие завершения |
|---|---|---|
| 0. Зафиксировать совместимость | Составить матрицу маршрут/условие/HTTP-статус/код/поля/заголовки. Включить ошибки обработчиков, middleware, 404/405 и webhook. Добавить проверки фактических ответов настоящего роутера | Есть baseline, различия существующих форматов названы явно |
| 1. Ввести общий рендерер | Добавить отдельный DTO ошибки, каталог кодов и единую запись. Поддержать `ContractError`, безопасную внутреннюю ошибку и прежние варианты `status` | Рендерер самостоятельно выдаёт полный контракт с `request_id`; старый `Errors` пока остаётся |
| 2. Перевести источники ошибок | Сначала категории и pause с явными специальными кодами. Затем задачи, аккаунт, auth, профиль, платежные create/sync и остальные подключённые обработчики. Перевести ошибки самого `Operation`, роутерные 404/405 | Каждый переведённый источник формирует правильный ответ без достройки глобальным middleware |
| 3. Закрыть инфраструктурные ответы и согласовать контракт | Настроить единый ответ rate limit с сохранением `Retry-After`. Обеспечить JSON-ответ восстановления после panic до начала записи. Обновить OpenAPI и клиентские проверки. Проверить смешанный запуск версий | Общие поля появляются во всех охваченных путях; HTTP-статусы и поведение frontend сохранены |
| 4. Убрать глобальную нормализацию | Удалить `Errors` и `defaultCode`, устаревшие реализации записи и текстовые эвристики, которые больше не нужны. Сохранить необходимые адаптеры совместимости | Настоящий роутер выдаёт корректные ошибки без перехвата и переписывания тела; регрессионные проверки пройдены |

Этапы следует выполнять небольшими проверяемыми изменениями. Нельзя удалить `Errors` сразу после добавления нового helper: неподключённые к нему обработчики, limiter или recoverer потеряют поля, которые сейчас добавляет этот middleware.

Для panic следует разделять два случая. До отправки заголовков можно сформировать единый HTTP 500. После начала записи невозможно гарантированно заменить уже отправленный ответ; нельзя дописывать второй JSON или пытаться менять HTTP-статус. Проверка этого поведения нужна при замене текущего recoverer.

### Области предполагаемых правок при реализации

- `backend/internal/http-server/apiresponse/`: новый общий рендерер, DTO и коды ошибок.
- `backend/internal/http-server/helpers/`, `backend/internal/lib/api/response/`: переходные адаптеры и последующее удаление дублирующей обработки ошибок с сохранением успешных ответов.
- Подключённые `backend/internal/http-server/handlers/` и middleware `auth`, `ratelimit`, `contracts`: явная передача кода и общего ответа.
- `backend/internal/http-server/router/router.go`: ответы 404/405, восстановление после panic и финальное удаление `Errors`.
- `frontend/src/lib/api.ts` и относящиеся тесты: типизация полей ошибки, обработка по коду и постепенное сокращение legacy-эвристик.
- `docs/openapi.yaml`: обязательность общих полей, тип `field_errors`, коды и документированные исключения.
- Тесты рендерера, middleware, настоящего роутера и затронутых пользовательских сценариев.

Эти пункты — план будущих изменений. При подготовке отчёта перечисленные файлы приложения не редактировались.

## 5. Границы совместимости

### Идемпотентность и транзакции

`Operation` и [postgres/operations.go](../backend/internal/storage/postgres/operations.go) остаются на прежнем механизме. Ответ обработчика со статусом от 400 приводит к откату; ошибки не сохраняются в `api_operations`; успешный ответ сохраняется вместе с изменениями данных.

При унификации ошибок нужно сохранить эти гарантии, прежние успешные ответы и отсутствие повторных after-commit действий при replay. Рефакторинг не меняет порядок блокировок, правила начисления наград или момент commit.

HTTP-статус важен также для [frontend/src/lib/commands.ts](../frontend/src/lib/commands.ts): после большинства 4xx ключ попытки удаляется, после 429 и ошибок сервера сохраняется. Переклассификация ошибки поэтому может изменить поведение повторной команды, даже при прежнем тексте сообщения.

### Авторизация и восстановление доступа

Сохраняются различия между 401 и временной недоступностью аккаунта, в том числе `503 ACCOUNT_UNAVAILABLE`. Унификация формата не меняет refresh, выход, проверки актуальных прав в БД или одинаковый ответ восстановления пароля для разных адресов.

### Webhook YooKassa

Webhook сохраняет отдельный контракт: пустой успешный ответ и предусмотренные текстовые ошибки. Его HTTP-статусы и семантика повтора провайдером не меняются. При удалении глобального `Errors` нужно сохранить поведение не только самого handler, но и ошибок ограничителя и recoverer на этом маршруте.

### Совместный запуск версий

Новая frontend-версия должна продолжать понимать старые ответы до обновления backend. Новые ответы backend должны сохранять поля, которые использует прежний клиент. Поэтому `error`, существующие `validation_errors`, текущие коды и варианты `status` не удаляются в первом изменении.

Переход `field_errors: null` к `{}` документируется и проверяется отдельно. Он соответствует описанному объектному типу OpenAPI, но всё равно является изменением наблюдаемого ответа.

## 6. Необходимые проверки при реализации

### Общий рендерер и преобразование ошибок

- Полный набор общих полей, правильный HTTP-статус и `Content-Type`, непустой `request_id` из контекста.
- Пустые ошибки полей представлены объектом; сообщения полей и индексы вроде `reminders.0` сохраняются.

## 7. Критерии завершения

- Все JSON-ошибки охваченного API формируются общим рендерером без разбора уже записанного ответа.
- Машинные коды назначаются явно и не зависят от языка или формулировки сообщения.
- Общие поля, типы и legacy-исключения соответствуют OpenAPI.
- `Errors` и `defaultCode` удалены; recorder внутри `Operation` сохранён до отдельного рефакторинга команд.
- Авторизация, повторные команды, транзакции, `Retry-After` и webhook сохраняют согласованное поведение.
- Неизвестная внутренняя причина доступна в диагностике с `request_id`, клиент получает безопасный ответ.
- Нужные регрессионные проверки пройдены; frontend сохраняет совместимость с предусмотренными старыми ответами.

Первый полезный результат — общий рендерер и перевод категорий/pause на явные коды при сохранённом `Errors`. Это небольшой участок, на котором можно проверить подход до массового переноса обработчиков.
