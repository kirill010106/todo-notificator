# План закрытого доступа к мониторингу и логам production

Дата: 21 октября 2026 года. Редакция 2 после повторного аудита HEAD `6c32fb8`. Статус: запланировано, не внедрено. [Результаты аудита и причины упрощений](PRIVATE-OBSERVABILITY-REVIEW-2026-10-21.md).

## Цель и объём

Разместить мониторинг и технические логи на том же сервере, где работает ToDo Notificator. Предоставить оператору доступ через SSH без публичных портов, доменов и маршрутов Traefik для служебных интерфейсов.

В контексте этого плана «проброс логирования» включает два результата:

1. Prometheus и Grafana работают на production-сервере; браузер оператора подключается через локальный SSH-туннель.
2. Технические stdout/stderr-логи контейнеров доступны через SSH с ограниченной глубиной просмотра и ротацией на сервере.

Prometheus хранит метрики, а не текстовые логи. На первом этапе Grafana показывает метрики; просмотр логов выполняется через Docker CLI. Централизованный поиск логов в Grafana через Loki и сборщик выделен в отдельный следующий этап ниже. Первый этап не следует принимать как реализацию поиска логов в Grafana.

Пользовательская история `activity-logger → MongoDB → /api/v1/me/logs` сохраняет текущие права доступа и best-effort-доставку. Доступ к MongoDB и gRPC через туннель в этот план не входит.

## Целевая схема первого этапа

| Компонент | Подключения | Доступ с компьютера оператора |
| --- | --- | --- |
| Backend metrics | `backend:9091`, существующая сеть Compose `default` | Напрямую не предоставляется |
| Prometheus | Сеть `default`, host binding `127.0.0.1:9090` | Через отдельный SSH-туннель при диагностике |
| Grafana | Сеть `default`, host binding `127.0.0.1:3001` | Через SSH-туннель и вход в Grafana |
| Логи приложения | Docker logging driver на сервере | Ограниченный просмотр через SSH |

Сохранить существующую сеть Compose и DNS-имена. Для требования «без публичного доступа» достаточно корректной loopback-публикации, отсутствия маршрутов reverse proxy и проверки внешней недоступности. Подключения и конфигурацию backend менять не требуется.

Для Prometheus/Grafana явно задать `traefik.enable=false`, не подключать сеть `traefik`, не использовать `network_mode: host`, `privileged` или Docker socket. Не добавлять DNS-записи и reverse proxy для этих интерфейсов. Проверить отсутствие альтернативной публикации через IPv6, host networking, сторонний прокси и прямую маршрутизацию Docker.

Все контейнеры общей сети проекта могут обращаться к служебным интерфейсам. Эта схема предполагает доверие к хосту и сервисам приложения; Prometheus не получает отдельную авторизацию для локального доступа. Если требуется защита от скомпрометированного frontend/email или посторонних контейнеров, выделить сеть `monitoring` с backend, Prometheus и Grafana отдельным изменением. `internal: true` дополнительно ограничивает внешний обмен контейнеров; само по себе это не заменяет настройки публикации, авторизацию и проверки. Такой вариант потребует проверки доступа хоста, обновления сетей backend и оценки исходящих соединений.

## Доступ оператора

Использовать индивидуальные SSH-ключи и строгую проверку заранее подтверждённого host key. Не отключать `StrictHostKeyChecking` и не доверять результату `ssh-keyscan` без независимой проверки. Приватный ключ CD не распространять операторам.

Пример будущего подключения с компьютера оператора, после внедрения и проверки ключа сервера:

```sh
ssh -N -T -o StrictHostKeyChecking=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:13001:127.0.0.1:3001 operator@prod.example.invalid
```

`operator` и `prod.example.invalid` — вымышленные значения существующего уполномоченного оператора и сервера. Для нестандартного SSH-порта добавить `-p <порт>`. Существующие записи `known_hosts` должны соответствовать этому порту.

Открыть [Grafana через туннель](http://127.0.0.1:13001). Для диагностики Prometheus при необходимости добавить второй forward `-L 127.0.0.1:19090:127.0.0.1:9090` и открыть [его UI](http://127.0.0.1:19090). Локальные порты также привязаны только к loopback. HTTP проходит внутри SSH до сервера; локальные пользователи компьютера и процессы на сервере остаются частью доверенной среды. Закрытие SSH завершает доступ через этот туннель, но не отзывает Grafana-сессию или другие подключения оператора.

На первом этапе использовать имеющийся персональный SSH-доступ администратора, не менять sshd и доступ CD ради туннеля. Если просмотр нужен человеку без административных прав, отдельно подготовить учётную запись только для forwarding: разрешённое назначение `127.0.0.1:3001`, при обоснованной необходимости также `127.0.0.1:9090`; запретить remote/agent/X11 forwarding и shell/произвольные команды. Проверить возможность `ssh -N` и отрицательные сценарии до выдачи такого доступа. Одного `PermitOpen` недостаточно, если пользователь сохраняет произвольный shell.

Логи читает существующий уполномоченный оператор. Не добавлять пользователя просмотра в группу `docker` и не выдавать произвольный `sudo docker`: это даёт широкое управление хостом. Ограниченный помощник для чтения логов нужен только при отдельном требовании делегировать их просмотр; в минимальный этап его разработка не входит.

## Защита Grafana и сетевых портов

- Явно отключить anonymous access и самостоятельную регистрацию: `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_USERS_ALLOW_SIGN_UP=false`. Сохранить вход по индивидуальным аккаунтам; для повседневного просмотра использовать Viewer, администрирование выполнять отдельно.
- Установить уникальный пароль администратора до первого запуска. Передавать его файлом через Compose secret и `GF_SECURITY_ADMIN_PASSWORD__FILE`, с доступом только нужному процессу и администратору хоста. Не помещать значение в Git, команды, общедоступные логи или вывод Compose. Такой secret в обычном Compose остаётся файлом хоста, а не зашифрованным хранилищем.
- Если `grafana_data` уже существует, проверить текущие аккаунты и отдельно сменить пароль штатным способом: переменная начального пароля не является процедурой ротации существующего аккаунта. Сохранить необходимые ключи шифрования Grafana при резервировании и восстановлении.
- Подготовку файла секрета включить в Ansible до первого запуска Grafana. Не вводить обязательную интерполяцию вида `${GRAFANA_PASSWORD:?}` в общий Compose: она может остановить разбор конфигурации выпуска приложения даже при выключенном мониторинге. Проверить, что disabled monitoring не требует новых секретов. Учесть фактические UID/GID контейнера и права чтения файла; одного `0600` у root-owned файла может быть недостаточно.
- Для первого этапа не устанавливать дополнительные плагины. Отключение телеметрии и автоматических проверок версий можно выполнить настройками Grafana; само по себе это не обеспечивает сетевую изоляцию. Обновления закреплённых образов остаются ответственностью оператора.
- Сохранить закрытыми host-порты `3000`, `3001`, `9090`, `9091`; для возможного следующего этапа — также `3100` и `12345`. Не изменять существующие публичные 80/443 приложения.
- Проверить cloud firewall и правила хоста с учётом Docker NAT; одного правила UFW недостаточно для подтверждения изоляции. Запретить внешнюю прямую маршрутизацию к служебным Docker-адресам.
- Проверить версию Docker Engine: документация отмечает доступность localhost-публикаций из того же L2-сегмента у версий до 28.0.0. При старой версии сначала запланировать поддерживаемое обновление или подтверждённую сетевую компенсацию; не считать loopback binding достаточной мерой сам по себе. [Docker: публикация портов](https://docs.docker.com/engine/network/port-publishing/)

## Хранение, нагрузка и состав логов

Начальные значения ниже — бюджет для внедрения, а не измеренные характеристики текущего сервера. До запуска проверить свободные RAM/CPU/диск и зарезервировать ресурсы для PostgreSQL, MongoDB и приложения. Если бюджет не помещается, сначала согласовать уменьшение хранения или увеличение ресурсов сервера.

| Данные/сервис | Начальная настройка | Ограничение |
| --- | --- | --- |
| Prometheus | Retention 7 дней, целевой размер TSDB 2 ГиБ; RAM 512 МиБ, CPU 0,5 | Retention не является жёсткой квотой диска: нужны запас под WAL, head и compaction и контроль фактического объёма |
| Grafana | Постоянный том; RAM 256 МиБ, CPU 0,5 | Проверить запуск, запросы и dashboards при выбранных лимитах |
| Логи контейнера | Сохранить фактический `json-file` или `local`; для них задать `max-size: "10m"`, `max-file: "3"` | Ориентир порядка 30 МБ на контейнер без учёта служебных расходов; срок в днях не гарантируется. Для иного драйвера отдельно проверить поддерживаемые опции |

Применять logging options на уровне выбранных сервисов проекта, без глобальной смены Docker daemon и без воздействия на посторонние проекты. Не менять драйвер или режим доставки только ради доступа по SSH. Настройки ротации вступают в силу после пересоздания контейнера. Для frontend/backend/email это согласовать со штатным выпуском. `deploy_release.py` также выполняет обычный `compose up -d mongo activity-logger`: при изменении образа/конфига Compose пересоздаёт эти контейнеры. Отдельный `--force-recreate` для них по умолчанию не нужен. Встроенная PostgreSQL запускается с `--no-recreate`; её ротацию и пересоздание планировать отдельно. [Поведение compose up](https://docs.docker.com/reference/cli/docker/compose/up/)

Если отдельно выбран non-blocking-режим, зафиксировать допустимость потери сообщений при заполнении буфера; blocking-режим способен создавать обратное давление. Ни один из них не даёт одновременно безусловную сохранность и отсутствие влияния на приложение. При удалении/пересоздании контейнера локальная история также может быть утрачена; нужный фрагмент инцидента сохранять заранее в защищённый каталог с ограниченным сроком хранения. Этот вариант не является долговечным аудитом. [Docker: режимы доставки и изменение настроек](https://docs.docker.com/engine/logging/configure/), [драйвер local](https://docs.docker.com/engine/logging/drivers/local/)

До фиксации RAM/retention измерить объём серий и расход памяти на стенде. В `middleware/metrics/metrics.go` при отсутствии шаблона маршрута label `path` берётся из `r.URL.Path`; неизвестные URL могут создавать новые серии. Указанные 512 МиБ не доказывают достаточность памяти или невозможность отказа. Проверка на ограниченном наборе тестовых 404 и штатных маршрутов нужна до выбора лимитов; возможное исправление middleware — отдельная задача, не реализованная этим планом.

До расширения доступа проверить весь путь записи логов на одноразовых данных. Не записывать JWT/refresh/reset/verification tokens, Authorization/Cookie, пароли, DSN, тела писем, произвольный `details_json` и содержимое пользовательских задач. Разрешённые поля: время, сервис, уровень, `request_id`, маршрут без query string, статус, длительность, безопасный код ошибки. IP и идентификаторы пользователей считать данными с ограниченным доступом; включать только при обоснованной диагностической потребности.

Отдельные задачи: убрать полный `details_json` из лога `LogEvent`; проверить ошибки драйверов БД/SMTP и Debug-логи email; сохранить безопасный frontend access-log. Не включать новые access-логи Traefik без проверки формата и фильтрации query/header-полей. Пароли не проверять чтением или публикацией production-логов.

Ограниченный просмотр на сервере существующим уполномоченным оператором:

```sh
cd /opt/todo-notificator
docker compose logs --since 15m --tail 200 --timestamps backend email-notifier activity-logger frontend
```

Для ручных Compose-команд также нужны `IMAGE_BASE` и `IMAGE_TAG` актуального выпуска: если их нет в серверном `.env`, передать через окружение, как описано в [инструкции выпуска](DEPLOYMENT.md). Явный список сервисов не отменяет интерполяцию остального Compose-файла.

Не пересылать необработанный вывод в чат, CI или публичные задачи. Включить наблюдение за свободным диском, перезапусками и достижением лимитов памяти; проверки хранения и ротации проводить на одноразовом стенде, без заполнения production-диска. В текущем scrape-конфиге нет host exporter: свободное место VM проверяет оператор существующими средствами; это не готовый dashboard/alert в Grafana.

| Порядок | Работа | Планируемые файлы/артефакты |
| --- | --- | --- |

| 2 | Очистить состав технических логов; проверить отсутствие вымышленных контрольных токенов и текстов задач в выводе | Затронутые Go log sites и тесты последствий |
| 3 | Закрепить проверенные версии и digest образов, добавить restart-policy, ресурсные настройки после измерения и ротацию; сохранить сети backend | `docker-compose.yml`, при необходимости отдельный конфиг Grafana в `deploy/grafana/` |
| 4 | Настроить retention, закрытый datasource и минимальные dashboards доступности, HTTP-ошибок/длительности | `prometheus.yml`, `deploy/grafana/provisioning/`, dashboards |
| 5 | Подготовить секрет Grafana, проверить существующий SSH-доступ и firewall; новые роли доступа добавлять по отдельной необходимости | Ansible tasks; значения секретов — вне Git |
| 6 | Добавить управляемый флаг `monitoring_enabled` и отдельный Ansible task file: проверка, pull, запуск двух сервисов, HTTP readiness и scrape | `ansible/deploy.yml`, новый `ansible/tasks/monitoring.yml`, `ansible/vars/production.yml` |
| 7 | Подключить эти tasks после успешного выпуска и обновить инструкцию | `docs/DEPLOYMENT.md`; workflow уже вызывает playbook и обычно не требует изменения |

Мониторинг остаётся в том же Compose-проекте с существующими `prometheus_data` и `grafana_data`. Перед внедрением сверить реальное имя проекта и томов; смена имени не должна незаметно создать пустую Grafana. Для двух сервисов можно добавить профиль `monitoring`, чтобы случайный общий `up` не запускал их. Профиль не является границей доступа и не нужен в командах, которые уже явно называют оба сервиса. Приложение от них не зависит через `depends_on`. [Правила Compose profiles](https://docs.docker.com/compose/how-tos/profiles/)

Ansible использует существующие пути `app_dir`, `.env` и то же имя Compose-проекта, что выпуск приложения. В каждой Compose-задаче передать `IMAGE_BASE: "{{ image_base }}"`, `IMAGE_TAG: "{{ release_tag }}"`, как у существующего release task: его process environment не сохраняется для последующих задач. Для мониторинга выполняются только `pull prometheus grafana` и `up -d --no-deps prometheus grafana`; никакого общего `up`, миграций и остановки приложения. На первом внедрении `monitoring_enabled` включается явно после подготовки секрета и проверки конфигурации. Выключение флага пропускает управление мониторингом, но не останавливает ранее работающие контейнеры; для отключения используется отдельная операция ниже.

Tasks подключаются после завершения `deploy_release.py`, вне его блока обработки неудачного выпуска. При отказе мониторинга Ansible/CD сообщает ошибку и факт, что приложение уже выпущено; приложение не останавливается и миграции не откатываются. Повторять только tasks мониторинга с проверкой готовности приложения, а не весь выпуск. Не требовать нового Python-сценария или Ansible collection для нескольких Compose-команд.

Для ожидания использовать `ansible.builtin.uri` на самом сервере, с `use_proxy: false`, timeout и ограниченными retries: Prometheus `http://127.0.0.1:9090/-/ready`, Grafana `http://127.0.0.1:3001/api/health` с проверкой состояния её БД. Затем отдельным Prometheus query API проверить `up{job="backend"} == 1`. HTTP 200 readiness не подтверждает scrape или закрытую авторизацию Grafana. Пароли/ответы с чувствительными данными не выводить. `--wait` без healthcheck подтверждает только running-состояние; наличие curl/wget внутри образа не требуется. Контейнерный healthcheck можно добавить при необходимости отдельной диагностики. Задать `restart: unless-stopped`. [Ansible uri](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/uri_module.html), [Prometheus readiness](https://prometheus.io/docs/prometheus/latest/management_api/)

## Приёмка первого этапа

Все пункты ниже — будущие проверки. Этот документ не подтверждает их прохождение.

1. На одноразовом окружении проверить итоговую Compose-конфигурацию без вывода секретов: bindings только `127.0.0.1`, нет host networking, Docker socket и сети Traefik у мониторинга; сети backend сохранены. С выключенным мониторингом и без его секрета конфигурация выпуска приложения продолжает разбираться.
2. Проверить конфиги средствами закреплённых образов. После запуска дождаться готовности Grafana/Prometheus, получить `up{job="backend"} == 1` и увидеть актуальные данные в Grafana. Выполнить только безопасные диагностические запросы без регистрации, писем и платежей.
3. С разрешённой внешней машины проверить недоступность служебных TCP-портов по публичным IPv4 и IPv6 сервера, а также отсутствие публичного HTTP-маршрута к мониторингу. Если есть риск старого Docker, отдельно проверить соседний L2-сегмент. Проверка только с самого сервера не подтверждает внешнюю изоляцию.
4. Через проверенный SSH-туннель открыть Grafana: без входа dashboards и данные недоступны, после входа Viewer видит dashboard и не может менять настройки; публичный health endpoint сам по себе не даёт доступ к данным. После закрытия туннеля доступ через него прекращается. Если добавлена роль только для forwarding, проверить запрет shell и неразрешённых назначений отдельно.
5. Проверить ротацию и отсутствие контрольных секретов на одноразовом стенде; переполнение буфера проверять только при выбранном non-blocking-режиме. Подтвердить, что ротация не обещает сохранение истории после пересоздания контейнера. Измерить число серий и расход ресурсов на штатных маршрутах и ограниченном наборе неизвестных URL.
6. Перезапустить мониторинг и Docker на стенде: нужные сервисы восстанавливаются, Grafana сохраняет настройки, Prometheus продолжает сбор. Остановка мониторинга не нарушает API и workers; перезагрузка всей VM требует отдельного окна, если проверяется в production.
7. Проверить ошибки Ansible tasks: неверный конфиг, недоступный образ, занятый порт, неготовый datasource. Приложение продолжает работу, ошибка мониторинга видна оператору, секреты не попадают в вывод. Повтор tasks не выпускает приложение заново и не сбрасывает тома. Проверить оба значения `monitoring_enabled`, включая сохранение ранее работающих контейнеров при false, и отдельный случай с `IMAGE_BASE`/`IMAGE_TAG` только в environment Ansible, без них в `.env`.
8. Для изменения Ansible выполнить syntax-check и перечисленные проверки tasks на стенде. Python unit tests запускаются, только если изменены соответствующие Python-скрипты/контракт конфигурации; проверки Go — для изменённых log sites. Полный CI и нагрузочная проверка не требуются для самого документа.

Результат приёмки записать отдельным датированным отчётом: версия/digest, среда, команда или способ проверки, наблюдение, ограничения. Не объявлять production защищённым только по результатам стенда.

## Отключение и восстановление

При проблеме остановить только `prometheus` и `grafana`, сохранив тома. Не использовать `docker compose down` для общего проекта и особенно `down -v`. Приложение и базы продолжают работу; закрытый просмотр логов по SSH остаётся доступен.

Конфиги и dashboards хранить в Git. Перед обновлением Grafana сделать согласованную резервную копию её тома и проверить восстановление на стенде; изменение версии может мигрировать её БД, поэтому возврат старого образа поверх нового тома не считать безопасным откатом. Откат требует совместимого snapshot/backup. Резервирование TSDB — отдельное решение: начально допускается потеря метрик, но не данных приложения.

## Следующий этап: поиск текстовых логов в Grafana

Если требуется единый поиск, добавить на тот же сервер Loki и Grafana Alloy после отдельной проработки способа чтения логов. Это расширение первого этапа; установка только Prometheus его не реализует.

Целевой поток: технические логи выбранных сервисов → сборщик → Loki → datasource Grafana. Loki и сборщик не публикуют host-порты, не подключаются к Traefik и не создают публичные ingest/query endpoints. Grafana остаётся единственным операторским UI через SSH; для Loki задаются отдельный том, retention, ограничения ingestion/query, памяти и диска.

До включения определить и проверить способ сбора без передачи Grafana/Loki полного Docker socket. Read-only mount socket не превращает Docker API в безопасный API чтения. Для сборщика отдельно оценить права на чтение логов и доступ к metadata/окружению контейнеров; не монтировать весь корень хоста. Не считать Docker logging-файлы универсальным публичным форматом для стороннего чтения.

В план расширения включить фильтрацию сервисов и полей, восстановление позиции чтения, дубли/пропуски после рестарта и пересоздания контейнера, ограниченную очередь и поведение при недоступности Loki. Labels ограничить низкой кардинальностью (`service`, `environment`, `level`); request/user IDs хранить как поля, без превращения каждого значения в отдельный label. Сбой сбора не должен блокировать рабочие запросы и отправку уведомлений.

Этот этап принимается отдельно: тестовое событие находится в Grafana, секреты исключены, внешнего доступа нет, лимиты и отказ Loki проверены на стенде. Прочность истории определяется выбранным хранилищем и backup; размещение на одной VM не переживает потерю всей VM без внешней копии. Удалённое хранение и оповещения требуют отдельного решения.
