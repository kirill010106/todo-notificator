# План закрытого доступа к мониторингу и логам production

Дата: 21 октября 2026 года. Статус: запланировано, не внедрено.

## Цель и объём

Разместить мониторинг и технические логи на том же сервере, где работает ToDo Notificator. Предоставить оператору доступ через SSH без публичных портов, доменов и маршрутов Traefik для служебных интерфейсов.

В контексте этого плана «проброс логирования» включает два результата:

1. Prometheus и Grafana работают на production-сервере; браузер оператора подключается через локальный SSH-туннель.
2. Технические stdout/stderr-логи контейнеров доступны через SSH с ограниченной глубиной просмотра и ротацией на сервере.

Prometheus хранит метрики, а не текстовые логи. На первом этапе Grafana показывает метрики; просмотр логов выполняется через Docker CLI. Централизованный поиск логов в Grafana через Loki и сборщик выделен в отдельный следующий этап ниже. Первый этап не следует принимать как реализацию поиска логов в Grafana.

Пользовательская история `activity-logger → MongoDB → /api/v1/me/logs` сохраняет текущие права доступа и best-effort-доставку. Доступ к MongoDB и gRPC через туннель в этот план не входит.

Наличие безопасного формата frontend access-log без query string не доказывает отсутствие чувствительных данных в остальных логах.

## Целевая схема первого этапа

| Компонент | Подключения | Доступ с компьютера оператора |
| --- | --- | --- |
| Backend metrics | `backend:9091`, отдельная сеть `monitoring` | Напрямую не предоставляется |
| Prometheus | Сеть `monitoring`, host binding `127.0.0.1:9090` | Только через SSH-туннель для диагностики |
| Grafana | Сеть `monitoring`, host binding `127.0.0.1:3001` | Через SSH-туннель и вход в Grafana |
| Логи приложения | Docker logging driver на сервере | Ограниченный просмотр через SSH |

Создать в существующем Compose-проекте сеть `monitoring` с `internal: true`. Подключить к ней backend, Prometheus и Grafana. Backend сохраняет сети, необходимые приложению; Prometheus/Grafana переводятся из `default` в `monitoring`. Provisioning продолжает использовать DNS-имя `prometheus`.

Для Prometheus/Grafana явно задать `traefik.enable=false`, не подключать сеть `traefik`, не использовать `network_mode: host`, `privileged` или Docker socket. Не добавлять DNS-записи и reverse proxy для этих интерфейсов. Проверить отсутствие альтернативной публикации через IPv6, host networking, сторонний прокси и прямую маршрутизацию Docker.

Изоляция сети не защищает от администратора хоста или скомпрометированного backend, который тоже подключён к `monitoring`. На сервере с посторонними недоверенными контейнерами потребуется дополнительное разделение доступа.

## Доступ оператора

Использовать индивидуальные SSH-ключи и строгую проверку заранее подтверждённого host key. Не отключать `StrictHostKeyChecking` и не доверять результату `ssh-keyscan` без независимой проверки. Приватный ключ CD не распространять операторам.

Пример будущего подключения с компьютера оператора, после внедрения и проверки ключа сервера:

```sh
ssh -N -T -o StrictHostKeyChecking=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:13001:127.0.0.1:3001 -L 127.0.0.1:19090:127.0.0.1:9090 monitoring-viewer@prod.example.invalid
```

`monitoring-viewer` и `prod.example.invalid` — вымышленные значения. Для нестандартного SSH-порта добавить `-p <порт>`. Существующие записи `known_hosts` должны соответствовать этому порту.

Открыть [Grafana через туннель](http://127.0.0.1:13001) и, при необходимости, [Prometheus через туннель](http://127.0.0.1:19090). Локальные порты также привязаны только к loopback. HTTP проходит внутри SSH до сервера; локальные пользователи компьютера и процессы на сервере остаются частью доверенной среды. Закрытие SSH завершает доступ.

Для учётной записи просмотра ограничить SSH forwarding: только local forwarding и назначения `127.0.0.1:3001`, `127.0.0.1:9090`; запретить agent/X11 forwarding и ненужный shell/команды. Проверить ограничения действующей конфигурации sshd, включая возможность `ssh -N`. Право просмотра контейнерных логов выдавать отдельно.

Не добавлять пользователя просмотра в группу `docker` и не выдавать произвольный `sudo docker`: это даёт широкое управление хостом. До появления ограниченного помощника логи читает существующий уполномоченный оператор. Будущий помощник должен разрешать только чтение логов фиксированного Compose-проекта и списка сервисов, ограничивать период/число строк и не принимать произвольные команды, пути, Compose-файлы и Docker options.

## Защита Grafana и сетевых портов

- Явно отключить anonymous access и самостоятельную регистрацию: `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_USERS_ALLOW_SIGN_UP=false`. Сохранить вход по индивидуальным аккаунтам; для повседневного просмотра использовать Viewer, администрирование выполнять отдельно.
- Установить уникальный пароль администратора до первого запуска. Передавать его файлом через Compose secret и `GF_SECURITY_ADMIN_PASSWORD__FILE`, с доступом только нужному процессу и администратору хоста. Не помещать значение в Git, команды, общедоступные логи или вывод Compose. Такой secret в обычном Compose остаётся файлом хоста, а не зашифрованным хранилищем.
- Если `grafana_data` уже существует, проверить текущие аккаунты и отдельно сменить пароль штатным способом: переменная начального пароля не является процедурой ротации существующего аккаунта. Сохранить необходимые ключи шифрования Grafana при резервировании и восстановлении.
- Отключить внешнюю телеметрию, проверки обновлений и установку плагинов во время работы; необходимые плагины включать в проверенный образ. Внутренняя сеть не должна требовать интернет-доступа Grafana для штатного просмотра.
- Сохранить закрытыми host-порты `3000`, `3001`, `9090`, `9091`; для возможного следующего этапа — также `3100` и `12345`. Не изменять существующие публичные 80/443 приложения.
- Проверить cloud firewall и правила хоста с учётом Docker NAT; одного правила UFW недостаточно для подтверждения изоляции. Запретить внешнюю прямую маршрутизацию к служебным Docker-адресам.
- Проверить версию Docker Engine: документация отмечает доступность localhost-публикаций из того же L2-сегмента у версий до 28.0.0. При старой версии сначала запланировать поддерживаемое обновление или подтверждённую сетевую компенсацию; не считать loopback binding достаточной мерой сам по себе. [Docker: публикация портов](https://docs.docker.com/engine/network/port-publishing/)

## Хранение, нагрузка и состав логов

Начальные значения ниже — бюджет для внедрения, а не измеренные характеристики текущего сервера. До запуска проверить свободные RAM/CPU/диск и зарезервировать ресурсы для PostgreSQL, MongoDB и приложения. Если бюджет не помещается, сначала согласовать уменьшение хранения или увеличение ресурсов сервера.

| Данные/сервис | Начальная настройка | Ограничение |
| --- | --- | --- |
| Prometheus | Retention 7 дней, целевой размер TSDB 2 ГиБ; RAM 512 МиБ, CPU 0,5 | Retention не является жёсткой квотой диска: нужны запас под WAL, head и compaction и контроль фактического объёма |
| Grafana | Постоянный том; RAM 256 МиБ, CPU 0,5 | Проверить запуск, запросы и dashboards при выбранных лимитах |
| Логи контейнера | Docker `local`, `max-size: "10m"`, `max-file: "3"`, `mode: "non-blocking"`, `max-buffer-size: "1m"` | Ориентир порядка 30 МБ на контейнер без учёта служебных расходов; срок в днях не гарантируется |

Применять logging options на уровне сервисов проекта, без глобальной смены Docker daemon и без воздействия на посторонние проекты. Настройки ротации вступают в силу после пересоздания контейнера. Для frontend/backend/email это согласовать со штатным выпуском; activity-logger и базы требуют явного плана пересоздания, поскольку текущий release-скрипт не гарантирует обновления их работающих контейнеров. Не перезапускать БД ради ротации без отдельного эксплуатационного окна.

Логи в non-blocking-режиме могут теряться при заполнении буфера. При удалении/пересоздании контейнера его локальная история также может быть утрачена; нужный фрагмент инцидента сохранять заранее в защищённый каталог с ограниченным сроком хранения. Этот вариант не является долговечным аудитом. [Docker: режимы доставки и изменение настроек](https://docs.docker.com/engine/logging/configure/), [драйвер local](https://docs.docker.com/engine/logging/drivers/local/)

До расширения доступа проверить весь путь записи логов на одноразовых данных. Не записывать JWT/refresh/reset/verification tokens, Authorization/Cookie, пароли, DSN, тела писем, произвольный `details_json` и содержимое пользовательских задач. Разрешённые поля: время, сервис, уровень, `request_id`, маршрут без query string, статус, длительность, безопасный код ошибки. IP и идентификаторы пользователей считать данными с ограниченным доступом; включать только при обоснованной диагностической потребности.

Отдельные задачи: убрать полный `details_json` из лога `LogEvent`; проверить ошибки драйверов БД/SMTP и Debug-логи email; сохранить безопасный frontend access-log. Не включать новые access-логи Traefik без проверки формата и фильтрации query/header-полей. Пароли не проверять чтением или публикацией production-логов.

Ограниченный просмотр на сервере существующим уполномоченным оператором:

```sh
cd /opt/todo-notificator
docker compose logs --since 15m --tail 200 --timestamps backend email-notifier activity-logger frontend
```

Не пересылать необработанный вывод в чат, CI или публичные задачи. Включить наблюдение за свободным диском, перезапусками и достижением лимитов памяти; проверки хранения и ротации проводить на одноразовом стенде, без заполнения production-диска.

| 5 | Подготовить SSH-учётные записи, секрет Grafana и проверки firewall без изменения доступа CD | Ansible tasks и шаблоны; значения секретов — вне Git |
| 6 | Добавить отдельный сценарий мониторинга: проверка, pull закреплённых образов, запуск только двух сервисов, ожидание готовности, проверка scrape | Новый `scripts/deploy_monitoring.py` и соответствующие тесты |
| 7 | Вызвать сценарий после успешной готовности приложения; обновить эксплуатационные инструкции | `ansible/deploy.yml`, `docs/DEPLOYMENT.md`, при необходимости `.github/workflows/cd.yml` |

Мониторинг остаётся в том же Compose-проекте с существующими `prometheus_data` и `grafana_data`. Перед внедрением сверить реальное имя проекта и томов; смена имени не должна незаметно создать пустую Grafana. Для двух сервисов добавить профиль `monitoring`; приложение от них не зависит через `depends_on`.

Отдельный сценарий должен использовать только явный список `prometheus grafana` и запуск с `--no-deps`; не выполнять общее `compose up`, не применять миграции и не останавливать приложение. Перевод backend в новую сеть выполняется при штатном выпуске до этого шага. Отказ мониторинга отображается отдельной ошибкой CD/сценария, но не вызывает откат схемы, остановку приложения или повторную отправку писем. Существующие работающие версии мониторинга по возможности сохраняются при ошибке предварительной проверки.

Предусмотреть ограниченное ожидание готовности и `restart: unless-stopped`. Healthcheck подобрать под фактический состав закреплённых образов, без предположения о наличии curl/wget. Проверка должна отличать готовность Prometheus от доступности scrape target backend.

## Приёмка первого этапа

Все пункты ниже — будущие проверки. Этот документ не подтверждает их прохождение.

1. На одноразовом окружении проверить итоговую Compose-конфигурацию без вывода секретов: bindings только `127.0.0.1`, нет host networking, Docker socket и сети Traefik у мониторинга; `monitoring` объявлена internal; сохранены нужные сети backend.
2. Проверить конфиги средствами закреплённых образов. После запуска дождаться готовности Grafana/Prometheus, получить `up{job="backend"} == 1` и увидеть актуальные данные в Grafana. Выполнить только безопасные диагностические запросы без регистрации, писем и платежей.
3. С разрешённой внешней машины проверить недоступность служебных TCP-портов по публичным IPv4 и IPv6 сервера, а также отсутствие публичного HTTP-маршрута к мониторингу. Если есть риск старого Docker, отдельно проверить соседний L2-сегмент. Проверка только с самого сервера не подтверждает внешнюю изоляцию.
4. Через проверенный SSH-туннель открыть Grafana: без входа данные недоступны, после входа Viewer видит dashboard и не может менять настройки. После закрытия туннеля локальные адреса недоступны. Проверить отклонение SSH forwarding на неразрешённые назначения.
5. Проверить ротацию, переполнение буфера и отсутствие контрольных секретов на одноразовом стенде. Подтвердить, что ротация не обещает сохранение истории после пересоздания контейнера.
6. Перезапустить мониторинг и Docker на стенде: нужные сервисы восстанавливаются, Grafana сохраняет настройки, Prometheus продолжает сбор. Остановка мониторинга не нарушает API и workers; перезагрузка всей VM требует отдельного окна, если проверяется в production.
7. Проверить ошибки отдельного сценария: неверный конфиг, недоступный образ, занятый порт, неготовый datasource. Приложение продолжает работу, ошибка мониторинга видна оператору, секреты не попадают в вывод.
8. Для изменения release/Ansible выполнить относящиеся к нему Python unit tests и syntax-check. Проверки Go нужны для изменённых log sites. Полный CI и нагрузочная проверка не требуются для самого документа.

Результат приёмки записать отдельным датированным отчётом: версия/digest, среда, команда или способ проверки, наблюдение, ограничения. Не объявлять production защищённым только по результатам стенда.

## Отключение и восстановление

При проблеме остановить только `prometheus` и `grafana`, сохранив тома. Не использовать `docker compose down` для общего проекта и особенно `down -v`. Приложение и базы продолжают работу; закрытый просмотр логов по SSH остаётся доступен.

Конфиги и dashboards хранить в Git. Перед обновлением Grafana сделать согласованную резервную копию её тома и проверить восстановление на стенде; изменение версии может мигрировать её БД, поэтому возврат старого образа поверх нового тома не считать безопасным откатом. Откат требует совместимого snapshot/backup. Резервирование TSDB — отдельное решение: начально допускается потеря метрик, но не данных приложения.

## Следующий этап: поиск текстовых логов в Grafana

Если требуется единый поиск, добавить на тот же сервер Loki и Grafana Alloy после отдельной проработки способа чтения логов. Это расширение первого этапа; установка только Prometheus его не реализует.

Целевой поток: технические логи выбранных сервисов → сборщик → Loki → datasource Grafana. Loki и сборщик не публикуют host-порты, не подключаются к Traefik и не создают публичные ingest/query endpoints. Grafana остаётся единственным операторским UI через SSH; для Loki задаются отдельный том, retention, ограничения ingestion/query, памяти и диска.

До включения определить и проверить способ сбора без передачи Grafana/Loki полного Docker socket. Read-only mount socket не превращает Docker API в безопасный API чтения. Для сборщика отдельно оценить права на чтение логов и доступ к metadata/окружению контейнеров; не монтировать весь корень хоста. Не считать Docker logging-файлы универсальным публичным форматом для стороннего чтения.

В план расширения включить фильтрацию сервисов и полей, восстановление позиции чтения, дубли/пропуски после рестарта и пересоздания контейнера, ограниченную очередь и поведение при недоступности Loki. Labels ограничить низкой кардинальностью (`service`, `environment`, `level`); request/user IDs хранить как поля, без превращения каждого значения в отдельный label. Сбой сбора не должен блокировать рабочие запросы и отправку уведомлений.

Этот этап принимается отдельно: тестовое событие находится в Grafana, секреты исключены, внешнего доступа нет, лимиты и отказ Loki проверены на стенде. Прочность истории определяется выбранным хранилищем и backup; размещение на одной VM не переживает потерю всей VM без внешней копии. Удалённое хранение и оповещения требуют отдельного решения.
