# Единый файл окружения

В каждом checkout используется один рабочий `.env` в корне. Локальная разработка и сервер имеют разные checkout и разные значения. `.env.example` — локальный шаблон, `.env.production.example` — серверный. Вложенные `.env` сервисов больше не читаются.

## Загрузка в Go

`pkg/envconfig.Load()` вызывается до инициализации backend, email, activity-logger и Telegram-заготовки. В backend загрузка также предшествует команде `migrate`.

1. Если переменная процесса `ENV_FILE` задана, читается только этот файл. Относительный `ENV_FILE` разрешается от текущей рабочей папки; для независимого запуска используйте абсолютный путь. Пустое значение, отсутствующий файл или ошибка разбора останавливают запуск без вывода содержимого файла.
2. Иначе загрузчик ищет вверх по дереву каталог с `go.work` и читает только `.env` этого каталога. `.env` в папке отдельного сервиса игнорируется.
3. Вне checkout окружение поступает только из процесса. Файл `.env` в произвольной рабочей папке не загружается. В checkout отсутствие корневого `.env` допустимо, если обязательные настройки уже переданы окружением; YAML по умолчанию остаётся локальным. Контейнеры используют явно заданные абсолютные пути.

Приоритет: переменные процесса, включая пустые значения, затем корневой `.env`, затем YAML и значения по умолчанию. `ENV_FILE` управляется только процессом, его значение внутри файла не меняет источник настроек. Не используйте `godotenv.Overload` и не выполняйте `.env` как PowerShell/shell-код.

`CONFIG_PATH` и `EMAIL_CONFIG_PATH`, если они относительные, разрешаются от каталога выбранного `.env` или найденного корня. Локальные значения по умолчанию:

```dotenv
CONFIG_PATH=backend/config/local.yaml
EMAIL_CONFIG_PATH=notifiers/email/config/local.yaml
```

Абсолютные пути сохраняются. Вне checkout относительные пути без `ENV_FILE` запрещены. Ошибочный `EMAIL_CONFIG_PATH` больше не заменяется молча локальным YAML.

## Локальный запуск

Создайте корневой `.env` из `.env.example`, укажите SMTP и секреты. Не копируйте шаблон поверх существующих настроек. `dev.ps1` передаёт дочерним процессам абсолютный `ENV_FILE` и больше не переопределяет DSN, MongoDB или пути конфигурации.

По умолчанию скрипт подготавливает PostgreSQL на `127.0.0.1:5433` и MongoDB на `127.0.0.1:27017` с демонстрационными локальными учётными данными. При своих адресах/учётных данных подготовьте базы самостоятельно и запускайте `./dev.ps1 -SkipDatabases`. Уже существующие переменные процесса имеют приоритет и могут менять адрес подключения.

Ручной запуск работает из папки сервиса: `go run ./cmd`. Также из корня: `go run ./backend/cmd`, `go run ./notifiers/email/cmd`, `go run ./activity-logger/cmd`. Для запуска бинарника из произвольной папки задайте абсолютный `ENV_FILE`.

После изменения `.env` остановите и снова запустите процесс вместе с Air: Air не следит за `.env`, а окружение, унаследованное от родительского процесса, имеет приоритет. Запущенные экземпляры продолжают работать со старой конфигурацией до перезапуска.

## Frontend и Docker

Vite ищет окружение в корне через `envDir: ".."`. Для рабочего окружения используйте один `.env`; не создавайте конкурирующие `.env.local` или `.env.<mode>` файлы. В браузер доступны только `VITE_*`; серверные секреты не должны иметь этот префикс.

`VITE_API_BASE_URL` встраивается при сборке. Для локального Vite используйте `/api/v1`, для production — `https://todoapi.chkpnk.ru/api/v1`. Изменение серверного `.env` не обновляет уже собранный JavaScript.

Docker-сборка frontend выполняется с контекстом `frontend/`, без корневого `.env`. Публичный адрес API задаётся аргументом сборки `VITE_API_BASE_URL`; Dockerfile по умолчанию использует production-адрес выше. Для другого домена передайте новый аргумент при сборке/в CD и пересоберите образ. Не передавайте production-файл с секретами в контекст сборки.

Production Compose подставляет значения из корневого `.env` и окружения процесса, затем передаёт каждому сервису только перечисленные настройки. Для PostgreSQL на том же сервере используются `POSTGRES_USER`, `POSTGRES_DB` и `POSTGRES_PASSWORD`; при отсутствии явного `DATABASE_URL` Compose формирует одинаковый внутренний DSN для backend, email и db-tools. Явный `DATABASE_URL` выбирает внешнюю БД; локальный DSN не следует копировать в production-файл. В email-контейнер не передаются платёжные ключи и `APP_SECRET`, в backend — SMTP-пароль. `CONFIG_PATH` и `EMAIL_CONFIG_PATH` задаются в Compose как `/app/config/prod.yaml`. Изменения окружения контейнера требуют пересоздания, обычного `restart` недостаточно. `TRUSTED_PROXIES` по умолчанию вычисляется при выпуске на сервере; вручную добавлять адрес не требуется. Режим `--check` не подключается к Docker, а реальный выпуск проверяет наличие прокси до остановки приложения. Подробнее: [DEPLOYMENT.md](DEPLOYMENT.md).

Сценарий выпуска использует абсолютный `--env-file <root>/.env`. Проверка без запуска/остановки контейнеров:

```powershell
python scripts/deploy_release.py --root . --backups .local-backups --check
```

## Переход и проверки

Перед переносом сохраните корневой и вложенные файлы в защищённый каталог вне Git и Docker-контекста, например `.local-backups/`. Сверьте конфликтующие значения: особенно `DATABASE_URL`, SMTP, webhook-секрет и ссылки. Не объединяйте файлы с разными БД автоматически. После заполнения корневого файла архивируйте вложенные `.env`, затем полностью перезапустите сервисы.

- `go test ./pkg/envconfig -count=1`: корень и папки сервисов, приоритет процесса, явный файл, контейнерный режим, абсолютные/относительные пути и безопасные ошибки.
- Тесты backend/config и email/config проверяют чтение типов и полей; сборка entrypoint-пакетов проверяет подключение общего загрузчика.
- `python -m unittest discover -s scripts -p 'test_release_config.py' -v`: настоящий Compose и production-шаблон, контейнерные пути и отсутствие чужих секретов в окружении сервисов.
- `npm test` и `npm run build`: frontend после смены каталога окружения. Реальные отправка SMTP и выпуск требуют отдельной проверки.
