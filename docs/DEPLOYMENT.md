# Безопасный выпуск в production

Production Compose использует внешнюю PostgreSQL и сеть `traefik`. Для локальной разработки остаётся `dev.ps1` и `backend/config/local.yaml` с автоматическими миграциями. В `prod.yaml` и production Compose автоматические миграции выключены: backend проверяет соответствие схемы встроенным миграциям и отказывается обслуживать запросы при несовпадении.

## Перед первым выпуском

- В `.env` должны быть реальные `DATABASE_URL`, секреты приложения и SMTP, а также `TRUSTED_PROXIES`: точные IP Traefik на сети, через которую он подключается к backend. Допускается узкий CIDR выделенной сети прокси. Не указывать всю private-сеть, loopback или весь интернет «на всякий случай». При изменении адреса Traefik обновлять настройку и перезапускать backend.
- Traefik должен сам формировать/дополнять `X-Forwarded-For` и не доверять входящим заголовкам от произвольных клиентов. Backend разбирает цепочку справа налево до первого недоверенного узла. `X-Real-IP` используется только при отсутствии цепочки и только от доверенного непосредственного прокси. Невалидная цепочка игнорируется целиком.
- Проверить на копии БД соглашение о старых датах: прежний браузер сохранял UTC в колонке deadline без пояса. Источник с иной конвенцией требует отдельного переноса.
- Остановить сторонние экземпляры backend/Air/notifier, которые используют ту же БД вне управляемого Compose. Сценарий останавливает только сервисы этого Compose-проекта; он не может обнаружить все внешние процессы.
- У хоста должны быть Docker Compose v2 с `up --wait`, Python 3 и место для резервной копии. `POSTGRES_TOOLS_IMAGE` по умолчанию `postgres:16-alpine`; версия `pg_dump` должна быть не старее сервера PostgreSQL.
- Проверить восстановление тестовой копии БД из архива. Автоматическая проверка ниже полностью читает архив, но не исполняет восстановление на production и не заменяет учебное восстановление.

## Запуск

CI публикует все четыре образа с тегом SHA коммита. Ansible принимает обязательный `release_tag` (40 символов SHA), получает именно этот commit и запускает `scripts/deploy_release.py`. Вручную на Linux-хосте из подготовленного checkout:

```sh
export IMAGE_BASE=ghcr.io/your-owner/todo-notificator
export IMAGE_TAG=<40-character-commit-sha>
python3 scripts/deploy_release.py --root /opt/todo-notificator --backups /opt/todo-notificator-backups
```

В `.env` должны быть заданы `TRUSTED_PROXIES` и остальные параметры. Скрипт требует `IMAGE_TAG` в окружении; он не выполняет `.env` как shell-код. Настоящий адрес прокси следует получить из конфигурации своего Traefik, пример из `.env.example` не является подходящим адресом по умолчанию.

Сценарий выполняет следующие шаги:

1. Захватывает блокировку выпуска на хосте, проверяет Compose и скачивает все необходимые образы. Ошибка до остановки не прерывает работающие сервисы.
2. Отключает автоперезапуск прежних frontend/backend/email-контейнеров, затем останавливает их с ожиданием до 60 секунд. Это не позволяет старому отправителю вернуться при перезапуске Docker во время переноса.
3. Создаёт полный PostgreSQL custom-архив в отдельном каталоге с правами 0700, файл — 0600. Проверяет сигнатуру, каталог и чтение/распаковку всех секций через `pg_restore`, сохраняет SHA-256. Миграция не запускается при ошибке любого этапа.
4. Запускает новый backend одноразово командой `backend migrate`, без HTTP и планировщиков. Миграция 00021 внутри транзакции сверяет число старых и перенесённых напоминаний. Повторный запуск не дублирует перенос.
5. Запускает инфраструктуру, затем пересоздаёт backend/frontend одной версии и ждёт их healthcheck. Backend уже не применяет миграции при старте.
6. Только после этого пересоздаёт email-notifier и ждёт его готовности. Новые контейнеры снова имеют штатную restart-policy из Compose.

Непосредственный `docker compose up -d` не выполняет резервное копирование и остановку старого отправителя: для обновлений использовать сценарий. При первоначальном пустом развёртывании сценарий также создаёт архив, применяет миграции и запускает сервисы.

## Если выпуск не удался

После начала остановки ошибка оставляет сервисы приложения остановленными; сценарий не запускает старую версию автоматически и не делает `goose down`. Он повторно отключает автоперезапуск частично созданных контейнеров. Проверить фактическое состояние контейнеров, если Docker был недоступен во время остановки.

Успешно проверенный архив имеет соседний `.dump.sha256`. Если создание/проверка упала, оставшийся файл может быть неполным — его нельзя считать проверенной копией. Архивы не удаляются автоматически. Задать отдельную политику хранения и защищённого внешнего копирования. Архив относится к одной БД; глобальные роли PostgreSQL и секреты окружения нужно сохранять отдельно.

Исправить причину и повторить выпуск той же версии либо подготовить восстановление БД из проверенного архива при полностью остановленных писателях. Откат на старый код после 00021 без восстановления БД не поддерживается. При сбое после запуска нового отправителя часть новых писем могла уже уйти: восстановление БД не отзывает доставленные письма.

## Лимиты запросов

Ограничения действуют на один процесс backend, окно — минута:

| Трафик | Лимит | Ключ |
|---|---|---|
| login и register вместе | 20 | Проверенный адрес клиента, IPv6 /64 |
| Публичные служебные запросы, refresh и verify | 100 | Проверенный адрес клиента, IPv6 /64 |
| Невалидные credentials защищённых маршрутов | 20 | Проверенный адрес клиента, IPv6 /64 |
| Авторизованные операции | 100 | ID аккаунта после проверки авторизации |
| YooKassa callback | 300 | Проверенный адрес клиента, IPv6 /64; бюджет независим от входа и приложения |

Readiness `/api/v1/health` имеет отдельное назначение и не расходует эти бюджеты. Доверенный IP не освобождает от лимитов. Callback сохраняет проверку источника YooKassa и сверку результата с провайдером. При нескольких репликах лимиты не становятся распределёнными — потребуется общий счётчик отдельно.

## Проверки

- Go: тесты определения адреса, поддельных заголовков, цепочек прокси, IPv6 и независимых бюджетов; интеграционный перенос с версии 20 и запрет старта на неподходящей схеме.
- `python -m unittest discover -s scripts -p 'test_deploy_release*.py' -v`: порядок выпуска и отказ до запуска отправителя при проблемах архива, миграции или готовности. С `RUN_RELEASE_INTEGRATION=1` также создаётся и восстанавливается архив на временной PostgreSQL с проверкой строк.
- CI проверяет синтаксис Ansible и запускает тесты выпуска. CD запускается только после успешного CI для push в main, собирает все образы с одним SHA и перед Ansible повторно сравнивает SHA с актуальной main. Поздно завершившийся старый CI не откатывает production. Автоматические выпуски сериализованы и не прерывают миграцию. Ручные выпуски нужно выполнять последовательно.

## Обновление до текущего релиза

Миграции 00021–00024 выполняются общим шагом выпуска: отдельные напоминания, серверный магазин, очередь подтверждений email и нормализация исторических часовых поясов. В 00024 неизвестные PostgreSQL значения (включая `Local`) заменяются на UTC; пользователю нужно заново выбрать свой пояс. Исходный пояс восстановить по строке `Local` невозможно.

Публикуются образы с SHA, без изменяемого тега `latest`. Для осознанного ручного отката используйте Ansible с конкретным `release_tag`; автоматический CD выпускает только актуальную main. Старый код допускается запускать только с совместимой схемой; иначе восстановите проверенный архив БД при остановленных сервисах.

Перед production-выпуском проверьте реальные SMTP и оплату на тестовом окружении, `TRUSTED_PROXIES`, секреты и внешний URL возврата. Локальные тесты не подтверждают настройки внешних сервисов. Запуск выпуска описан выше; подготовка к релизу сама по себе не выполняет деплой.
