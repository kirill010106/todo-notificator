# Безопасный выпуск в production

Production Compose по умолчанию запускает PostgreSQL 16 на том же сервере в отдельном контейнере с постоянным томом и использует существующую сеть `traefik`. Внешняя PostgreSQL остаётся доступна через явный `DATABASE_URL`. Для локальной разработки остаётся `dev.ps1` и `backend/config/local.yaml` с автоматическими миграциями. В `prod.yaml` и production Compose автоматические миграции выключены: backend проверяет соответствие схемы встроенным миграциям и отказывается обслуживать запросы при несовпадении.

## Перед первым выпуском

CD автоматически подготавливает Ubuntu 22.04/24.04/26.04/26.10: устанавливает Git, Python, Docker Engine и Compose из официального Docker APT-репозитория, включает Docker и создаёт bridge-сеть `traefik`. Существующие версии пакетов не обновляются принудительно. Другие установленные контейнерные runtime не удаляются: конфликт требует отдельного переноса.

Первоначально оператор задаёт SSH-доступ пользователя с passwordless sudo, DNS для `todo.chkpnk.ru` и `todoapi.chkpnk.ru` на публичный адрес VM, разрешает SSH и входящие TCP 80/443 в firewall сервера и облака. Ansible не меняет DNS, firewall и ключи доступа.

В GitHub Settings → Secrets and variables → Actions нужны:

- Secrets: `SERVER_IP` (только хост/IP), `SERVER_USER`, `SSH_PRIVATE_KEY`, `SSH_HOST_PUBLIC_KEY` (заранее проверенный публичный ключ сервера), `PROD_ENV_FILE` (заполненный production `.env`).
- Variables: `DEPLOY_ENABLED=true`, `ACME_EMAIL` (действующий email для Let's Encrypt), опционально `SERVER_SSH_PORT` (по умолчанию `22`).

Для нестандартного `SERVER_SSH_PORT` проверенный ключ записывается в `known_hosts` как `[host]:port`; Ansible подключается к тому же порту. Для порта `22` используется обычная запись хоста.

Если Traefik в сети отсутствует, Ansible создаёт отдельный проект `todo-edge` с конфигурацией `/opt/todo-traefik/compose.yml`, портами 80/443 и именованным томом сертификатов `todo-edge_certificates`. Используются entrypoint `web-secure`, resolver `default` и HTTP-01 с перенаправлением HTTP на HTTPS. Email задаётся переменной `ACME_EMAIL` на runner или `-e acme_email=...` при ручном запуске Ansible. Сертификаты запрашиваются после появления маршрутов приложения; локальная готовность прокси не подтверждает DNS и доступность Let's Encrypt снаружи.

Повторный выпуск использует тот же проект и том. Не удалять том сертификатов. Единственный уже установленный официальный Traefik в сети, включая созданный вручную в `/opt/traefik`, используется без замены конфигурации; остановленный контейнер запускается. Его entrypoints, TLS resolver и DNS оператор должен согласовать с приложением. Несколько Traefik требуют явного выбора. Проверка Docker, Compose и готовности прокси выполняется до сценария выпуска приложения. Приватный ключ и содержимое `.env` не выводятся в журнал; параметры Ansible передаются JSON-файлом с ограниченным доступом.

Автоматическая подготовка не выполняет обновление Docker или Traefik до новой версии при каждом выпуске. Управляемый образ задан в `ansible/vars/production.yml`; его обновление — отдельное изменение конфигурации. Выпуск приложения по-прежнему архивирует БД перед миграциями и сохраняет её том.

- Для CD сохранить в GitHub Actions secret `SSH_HOST_PUBLIC_KEY` заранее проверенный публичный host key сервера: одну строку из `/etc/ssh/ssh_host_ed25519_key.pub` (тип ключа и base64, комментарий допустим). Получить её через доверенную консоль провайдера/сервера и проверить fingerprint командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`. Этот ключ удостоверяет **сервер**; существующий `SSH_PRIVATE_KEY` удостоверяет пользователя деплоя и остаётся отдельным секретом. `SERVER_IP` должен содержать ровно один IP или DNS-hostname, без порта, пробелов и wildcard.
- CD связывает этот ключ с `SERVER_IP` в отдельном `known_hosts` и включает строгую проверку у Ansible/OpenSSH. Пустой/некорректный ключ останавливает job до загрузки приватного ключа и создания production `.env`; неизвестный/изменившийся ключ останавливает SSH до аутентификации. Другие known_hosts и DNS SSHFP не используются как альтернативное доверие. При замене ключа сначала заново проверить его через доверенную консоль, затем обновить `SSH_HOST_PUBLIC_KEY`. Не заменять эту процедуру слепым доверием результату сетевого `ssh-keyscan`.
- В отдельном production checkout скопировать `.env.production.example` в `.env` и заменить все `REPLACE_WITH_...`. Не перезаписывать локальный `.env`: окружения разработки и выпуска различаются. `IMAGE_BASE` — префикс образов в реестре, `IMAGE_TAG` — SHA коммита, для которого CI уже опубликовал все четыре образа. Случайный SHA или `latest` не подходят.
- В `.env` должны быть реальные `POSTGRES_PASSWORD`, секреты приложения и SMTP. Для внешней БД вместо встроенной задаётся `DATABASE_URL`. `TRUSTED_PROXIES` по умолчанию имеет значение `auto`: сценарий выпуска сам определяет точный IP Traefik в выбранной Docker-сети. Вручную искать и переносить IP не требуется. Для нестандартной инфраструктуры сохраняется явное переопределение IP/CIDR; не указывать всю private-сеть, loopback или весь интернет.
- Traefik должен сам формировать/дополнять `X-Forwarded-For` и не доверять входящим заголовкам от произвольных клиентов. Backend разбирает цепочку справа налево до первого недоверенного узла. `X-Real-IP` используется только при отсутствии цепочки и только от доверенного непосредственного прокси. Невалидная цепочка игнорируется целиком.
- Проверить на копии БД соглашение о старых датах: прежний браузер сохранял UTC в колонке deadline без пояса. Источник с иной конвенцией требует отдельного переноса.
- Остановить сторонние экземпляры backend/Air/notifier, которые используют ту же БД вне управляемого Compose. Сценарий останавливает только сервисы этого Compose-проекта; он не может обнаружить все внешние процессы.
- У хоста должны быть Docker Compose v2 с `up --wait`, Python 3 и место для резервной копии. `POSTGRES_TOOLS_IMAGE` по умолчанию `postgres:16-alpine`; версия `pg_dump` должна быть не старее сервера PostgreSQL.
- Проверить восстановление тестовой копии БД из архива. Автоматическая проверка ниже полностью читает архив, но не исполняет восстановление на production и не заменяет учебное восстановление.

## Запуск

Сначала проверить конфигурацию без скачивания образов, остановки, миграций и запуска контейнеров. Проверка работает также в Windows с Python и Docker Compose; Docker Engine для неё не требуется:

```powershell
python scripts/deploy_release.py --root . --backups .local-backups --check
```

Проверка читает итоговую конфигурацию Compose с учётом окружения процесса и `.env`, но не выводит секреты. Проверяются единые образы с SHA, production-режим без автоматических миграций, обязательные секреты, доступные из контейнеров адреса, HTTPS-ссылки, SMTP-поля и согласованность пары настроек YooKassa. `CLIENT_URL`, `APP_URL`, `WEBHOOK_URL`, `ACTIVITY_LOGGER_ADDR` и `MONGO_URL` задаются по production-шаблону; Compose имеет серверные значения по умолчанию для внутренних адресов и URL. Тот же шаг автоматически выполняется перед выпуском до скачивания и остановки сервисов. В режиме `--check` значение `auto` проверяется как режим конфигурации без обращения к Docker Engine. При настоящем выпуске адрес определяется на сервере до скачивания образов и остановки сервисов. Успех статической проверки не подтверждает наличие Traefik на сервере, доступность БД/SMTP, существование образов или настройки DNS.

CI публикует все четыре образа с тегом SHA коммита. Ansible принимает обязательный `release_tag` (40 символов SHA), получает именно этот commit и запускает `scripts/deploy_release.py`. Вручную на Linux-хосте из подготовленного checkout:

```sh
export IMAGE_BASE=ghcr.io/your-owner/todo-notificator
export IMAGE_TAG=<40-character-commit-sha>
python3 scripts/deploy_release.py --root /opt/todo-notificator --backups /opt/todo-notificator-backups
```

`IMAGE_BASE` и `IMAGE_TAG` можно задать в `.env` или окружении процесса; переменные процесса имеют приоритет. Скрипт читает итоговые значения через Compose и не выполняет `.env` как shell-код. `TRUSTED_PROXIES` можно не задавать: используется автоматическое определение на сервере. Существующий Ansible/CD запускает этот же сценарий, отдельного шага оператора не требуется.

Сценарий выполняет следующие шаги:

1. Захватывает блокировку выпуска на хосте, проверяет Compose, при `TRUSTED_PROXIES=auto` находит Traefik и передаёт его точные адреса всем последующим командам Compose через окружение процесса, затем скачивает все необходимые образы. Если используется встроенная PostgreSQL, запускает её с `--no-recreate` и ждёт healthcheck. Через отдельный db-tools-контейнер проверяет реальную авторизацию запросом `SELECT 1`. Ошибка до остановки не прерывает работающие сервисы приложения; новый контейнер БД и том могут уже быть созданы.
2. Отключает автоперезапуск прежних frontend/backend/email-контейнеров, затем останавливает их с ожиданием до 60 секунд. Это не позволяет старому отправителю вернуться при перезапуске Docker во время переноса.
3. Создаёт полный PostgreSQL custom-архив в отдельном каталоге с правами 0700, файл — 0600. Проверяет сигнатуру, каталог и чтение/распаковку всех секций через `pg_restore`, сохраняет SHA-256. Миграция не запускается при ошибке любого этапа.
4. Запускает новый backend одноразово командой `backend migrate`, без HTTP и планировщиков. Миграция 00021 внутри транзакции сверяет число старых и перенесённых напоминаний. Повторный запуск не дублирует перенос.
5. Запускает инфраструктуру, затем пересоздаёт backend/frontend одной версии и ждёт их healthcheck. Backend уже не применяет миграции при старте.
6. Только после этого пересоздаёт email-notifier и ждёт его готовности. Новые контейнеры снова имеют штатную restart-policy из Compose.

Непосредственный `docker compose up -d` не выполняет резервное копирование и остановку старого отправителя: для обновлений использовать сценарий. При первоначальном пустом развёртывании сценарий также создаёт архив, применяет миграции и запускает сервисы.

## PostgreSQL на том же сервере

В серверном `.env` / GitHub secret `PROD_ENV_FILE` достаточно:

```dotenv
POSTGRES_USER=todo
POSTGRES_DB=todo
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_POSTGRES_PASSWORD_AT_LEAST_32_CHARACTERS
```

Сгенерировать пароль: `python -c "import secrets; print(secrets.token_hex(32))"`. Для автоматического формирования URI используйте URL-safe пароль без пробелов, `$`, `@`, `:` и других разделителей; сгенерированная hex-строка подходит. Прежнюю строку `DATABASE_URL` нужно удалить из production-файла: явный DSN имеет приоритет и выбирает другую БД.

Compose одинаково формирует `DATABASE_URL` для backend, email и db-tools: `postgres://todo:<password>@postgres:5432/todo?sslmode=disable`. Имена и пароль берутся из `POSTGRES_*`. Хост `postgres` — внутреннее DNS-имя сервиса Docker, отдельный домен и публичный IP не нужны. TLS в контейнере PostgreSQL не настроен, поэтому для этого внутреннего подключения используется `sslmode=disable`; внешний DSN требует собственных настроек TLS.

Сценарий выпуска автоматически скачивает `postgres:16-alpine`, создаёт контейнер/пользователя/БД при первом запуске, ждёт готовности и проверяет пароль. Далее выполняет архивирование, миграции и запуск приложения в обычном порядке. Порт 5432 на хост не публикуется, контейнер подключён только к внутренней сети проекта и не подключён к Traefik.

Данные сохраняются в именованном томе `postgres_data` этого Compose-проекта. Обычные перезапуски и пересоздание контейнера сохраняют данные. Не меняйте имя Compose-проекта при обновлении и не удаляйте этот том / не используйте `docker compose down -v` для production: это удаляет БД. Архивы выпуска — отдельные `.dump` с checksum; необходима также внешняя копия архивов на случай потери самого сервера.

`POSTGRES_USER`, `POSTGRES_DB` и `POSTGRES_PASSWORD` инициализируют только пустой том. Изменение этих значений в `.env` не меняет существующих пользователей/паролей и не создаёт новую БД в прежнем томе. Несоответствие пароля обнаруживается проверкой соединения до остановки приложения. Смена пароля существующей БД выполняется отдельной операцией SQL с согласованным обновлением окружения.

При обновлении приложения существующий PostgreSQL не пересоздаётся автоматически, даже если скачан более новый образ. Обновление самой БД — отдельная операция обслуживания с проверенным архивом; смена major-версии не выполняется простой заменой тега образа.

Для уже существующей внешней БД задайте полный `DATABASE_URL` с хостом, отличным от `postgres`: встроенный сервис не запускается и данные автоматически не переносятся. Сервис `postgres` находится в профиле `database`, который сценарий выпуска включает сам. Локальная разработка продолжает использовать свой прежний DSN и `dev.ps1`.

## Автоматическое определение доверенного прокси

Traefik принимает внешний запрос и передаёт backend сведения об исходном IP. Backend доверяет таким заголовкам только от разрешённого адреса прокси: это нужно для лимитов запросов и проверки источника платёжных callback. Доверять заголовкам от любого клиента нельзя.

При `TRUSTED_PROXIES=auto` (также при отсутствии/пустом значении в `.env`) сценарий читает выбранную сеть из `traefik.docker.network` у backend и проверяет, что она подключена как внешняя. Через Docker inspect он находит ровно один запущенный контейнер официального Traefik в локальной bridge-сети. Поддерживаются имена образов `traefik`, `library/traefik`, `docker.io/traefik`, `docker.io/library/traefik`, `dhi.io/traefik` с тегами или digest. Имя контейнера значения не имеет.

В backend передаются только текущие адреса этого контейнера: IPv4 `/32` и при наличии IPv6 `/128`. Подсеть целиком и остальные контейнеры доверенными не становятся. Результат повторно проверяется через Compose, `.env` не переписывается. Docker inspection не выводится в журнал, так как в нём могут быть секреты.

Если сеть/прокси отсутствует, прокси несколько, адрес изменился во время проверки или Docker недоступен, выпуск завершается до остановки приложения. На каждом новом выпуске адрес определяется заново. Если Traefik отдельно пересоздан с другим IP после выпуска, нужно повторить deployment pipeline; непрерывного наблюдения за внешним Traefik этот сценарий не выполняет. Для host/overlay-сетей, нескольких прокси и нестандартного образа задайте явные IP/CIDR.

Backend сам значение `auto` не принимает: запуск и обновление backend выполняются через `deploy_release.py`/CD, который заменяет его адресами. Прямой `docker compose up backend` не является сценарием выпуска. Локальная разработка через `dev.ps1`/Go не использует Compose-значение `auto` и работает с прямыми подключениями.

## Если выпуск не удался

После начала остановки ошибка оставляет сервисы приложения остановленными; сценарий не запускает старую версию автоматически и не делает `goose down`. Он повторно отключает автоперезапуск частично созданных контейнеров. Проверить фактическое состояние контейнеров, если Docker был недоступен во время остановки.

Успешно проверенный архив имеет соседний `.dump.sha256`. Если создание/проверка упала, оставшийся файл может быть неполным — его нельзя считать проверенной копией. Архивы не удаляются автоматически. Задать отдельную политику хранения и защищённого внешнего копирования. Архив относится к одной БД; глобальные роли PostgreSQL и секреты окружения нужно сохранять отдельно.

Исправить причину и повторить выпуск той же версии либо подготовить восстановление БД из проверенного архива при полностью остановленных писателях. Откат на старый код после 00021 без восстановления БД не поддерживается. При сбое после запуска нового отправителя часть новых писем могла уже уйти: восстановление БД не отзывает доставленные письма.

## Лимиты запросов

Ограничения действуют на один процесс backend, окно — минута:

| Трафик | Лимит | Ключ |
|---|---|---|
| login и register вместе | 20 | Проверенный адрес клиента, IPv6 /64 |
| Публичные служебные запросы, refresh и verify | 100 | Проверенный адрес клиента, IPv6 /64 |
| Невалидные credentials защищённых маршрутов | 20 | Проверенный адрес клиента, IPv6 /64 |
| Авторизованные операции | 100 | ID аккаунта после проверки авторизации |
| YooKassa callback | 300 | Проверенный адрес клиента, IPv6 /64; бюджет независим от входа и приложения |

Readiness `/api/v1/health` имеет отдельное назначение и не расходует эти бюджеты. Доверенный IP не освобождает от лимитов. Callback сохраняет проверку источника YooKassa и сверку результата с провайдером. При нескольких репликах лимиты не становятся распределёнными — потребуется общий счётчик отдельно.

## Проверки

- Go: тесты определения адреса, поддельных заголовков, цепочек прокси, IPv6 и независимых бюджетов; интеграционный перенос с версии 20 и запрет старта на неподходящей схеме.
- `python -m unittest discover -s scripts -p 'test_deploy_release*.py' -v`: порядок выпуска и отказ до запуска отправителя при проблемах архива, миграции или готовности. С `RUN_RELEASE_INTEGRATION=1` также создаётся и восстанавливается архив на временной PostgreSQL с проверкой строк.
- `python -m unittest discover -s scripts -p 'test_release_config.py' -v`: отклонение локальных/неполных настроек, смешанных версий и проверка настоящего Compose с заполненным production-шаблоном (нужен Docker CLI, без запуска контейнеров).
- CI проверяет синтаксис Ansible и запускает тесты выпуска. CD запускается только после успешного CI для push в main, собирает все образы с одним SHA и перед Ansible повторно сравнивает SHA с актуальной main. Поздно завершившийся старый CI не откатывает production. Автоматические выпуски сериализованы и не прерывают миграцию. Ручные выпуски нужно выполнять последовательно.
- `python -m unittest discover -s scripts -p 'test_configure_deploy_ssh.py' -v` проверяет привязку ключа к хосту и отказ при некорректной настройке; backend-тест `TestDeploymentRejectsSubstitutedHostKey` запускает локальные SSH-заглушки и настоящий клиент OpenSSH, подтверждая допуск проверенного ключа и отказ подменённому до аутентификации. Нужны Python 3, `ssh`, `ssh-keygen` и разрешённый loopback; внешние серверы и реальные SSH-credentials не используются.

## Обновление до текущего релиза

Миграция `00026_hash_refresh_tokens.sql` отзывает **все существующие refresh-сессии** и заменяет колонку `token` на `token_hash`. Новый backend сохраняет и сравнивает только SHA-256 случайного токена; API продолжает возвращать браузеру исходный случайный токен. После выпуска потребуется повторный вход при следующем обновлении сессии. Уже выданные access JWT действуют до своего срока истечения; эта миграция не меняет `auth_version` пользователей.

Применять 00026 нужно общим сценарием выпуска при остановленных писателях. Старый backend несовместим с новой колонкой и не должен работать параллельно с новым. Down-миграция тоже удаляет refresh-сессии: восстановить исходные токены из хешей невозможно. Данные пользователей, паролей и email-outbox сохраняются. Восстановление архива до 00026 возвращает открытые токены и требует их повторного отзыва до открытия сервиса; запуск старого кода возвращает исходный риск хранения секретов.

Миграции 00021–00024 выполняются общим шагом выпуска: отдельные напоминания, серверный магазин, очередь подтверждений email и нормализация исторических часовых поясов. В 00024 неизвестные PostgreSQL значения (включая `Local`) заменяются на UTC; пользователю нужно заново выбрать свой пояс. Исходный пояс восстановить по строке `Local` невозможно.

Публикуются образы с SHA, без изменяемого тега `latest`. Для осознанного ручного отката используйте Ansible с конкретным `release_tag`; автоматический CD выпускает только актуальную main. Старый код допускается запускать только с совместимой схемой; иначе восстановите проверенный архив БД при остановленных сервисах.

Перед production-выпуском проверьте реальные SMTP и оплату на тестовом окружении, работу Traefik, секреты и внешний URL возврата. Локальные тесты не подтверждают настройки внешних сервисов. Запуск выпуска описан выше; подготовка к релизу сама по себе не выполняет деплой.

## Изменение только SMTP и мониторинг

При уже выпущенной текущей версии обновить SMTP-поля в серверном `.env`, выполнить `--check`, затем на сервере:

```sh
docker compose up -d --no-deps --force-recreate --wait email-notifier
```

Эта команда подходит для изменения конфигурации отправителя при совместимой схеме БД; новую версию приложения выпускать общим сценарием. Локальный Air-процесс использует корневой `.env`: после изменения SMTP полностью перезапустить его. Вложенные `.env` больше не читаются. Правила путей и приоритетов описаны в [ENVIRONMENT.md](ENVIRONMENT.md). Production Compose не предназначен для локального запуска одного отправителя.

Prometheus собирает `backend:9091` по внутренней сети Compose. Prometheus (`127.0.0.1:9090`) и Grafana (`127.0.0.1:3001`) доступны на loopback сервера; для доступа с компьютера использовать SSH-туннель. Сценарий выпуска запускает приложение; при необходимости мониторинг включить отдельно после успешного выпуска:

```sh
docker compose up -d --no-deps prometheus grafana
```


### Аккаунт и восстановление пароля (00025)

Перед выпуском применить `00025_account_security.sql`, затем обновить backend и email-worker, после них frontend. Миграция сохраняет текущие ссылки подтверждения, привязывая их к текущему email; существующие аккаунты получают пустое имя и версию авторизации 0. Старые JWT работают до первого изменения учётных данных. После смены почты/пароля версия увеличивается, прежние access и refresh tokens отклоняются.

Email-worker также обслуживает `password_reset_outbox`. Проверить настроенный адрес приложения (`app_url`), доставку `/reset-password?token=…` и заголовок `Referrer-Policy: no-referrer` на frontend. Конфигурация frontend nginx записывает только путь без query string и заголовка Referer, чтобы секреты из ссылок не попадали в журнал доступа. Провести проверку восстановления на тестовом аккаунте; следить за ошибками доставки и количеством записей `failed` в очереди без вывода токенов.
