# Повторный аудит плана закрытого мониторинга и логов

Дата: 21 октября 2026 года. Проверенный HEAD: `6c32fb8`. Перед началом рабочая копия была чистой. Объект: первоначальная редакция [плана](PRIVATE-OBSERVABILITY-PLAN.md) в этом HEAD, её соответствие исходникам, границы задачи и сложность внедрения.

## Вывод

Закрытый доступ через loopback и SSH соответствует задаче. Большая часть необходимой сетевой конфигурации уже существует. Рекомендуется сохранить текущие сети приложения, настроить Grafana, воспроизводимый запуск и хранение, затем добавить небольшой Ansible task file после выпуска. Новый Python-сценарий, обязательная перестройка сетей и смена log driver для этого не требуются.

План обновлён до редакции 2. Ни одно изменение приложения или инфраструктуры из него не внедрено. Просмотр технических логов на минимальном этапе остаётся в SSH; поиск этих логов непосредственно в Grafana требует отдельного внедрения Loki/сборщика.

## Проверка замечаний к первой редакции

Номера A1–A8 относятся к этому аудиту плана. Это замечания к проектному решению и его описанию, а не список воспроизведённых production-уязвимостей; категории P1/P2/P3 им не присваиваются. Для каждого пункта ниже указан способ проверки и предел вывода.

### A1. Обязательная новая сеть расширяла изменение без необходимости для закрытого доступа

Место первой редакции: «Целевая схема первого этапа», обязательные `monitoring`/`internal: true` и перевод backend в новую сеть. Источник: `docker-compose.yml:148–162`, `ansible/templates/traefik-compose.yml.j2`, раздел мониторинга `docs/DEPLOYMENT.md:153`.

Проверка: прочитаны host bindings и сети сервисов, настройки Docker provider Traefik, текущая инструкция. Наблюдение: служебные порты уже привязаны к `127.0.0.1`; у Prometheus/Grafana нет сети Traefik и HTTP-router labels, в управляемом Traefik отключён exposed-by-default. Это подтверждает конфигурацию репозитория, но не фактический firewall/прокси сервера.

Последствие прежнего решения: дополнительное пересоздание backend и сетевые проверки ради требования, которое можно выполнить текущими bindings. Отдельная сеть полезна при необходимости изоляции от других сервисов, но это более сильная модель угроз.

Изменение плана: сохранена существующая сеть `default`; выделенная сеть стала условным усилением. Остаточный риск описан: сервисы общей сети и администратор хоста имеют доступ к Prometheus. Проверка внешней недоступности остаётся обязательной.

### A2. Новый Python-сценарий дублировал существующий слой Ansible

Место первой редакции: таблица внедрения, новый `scripts/deploy_monitoring.py`. Источники: `ansible/deploy.yml`, `scripts/deploy_release.py:116–148`.

Проверка: прослежен путь CD → Ansible → release script. Наблюдение: уже есть точка добавления отдельной задачи после готовности приложения; для мониторинга достаточно адресного pull/up и HTTP-проверок. Установка дополнительной Ansible collection не нужна: `ansible.builtin.command`/`uri` входят в существующий подход.

Последствие: отдельная программа, аргументы, обработка ошибок и тестовый набор без новой требуемой функции. Кроме того, добавление мониторинга внутрь exception-блока release script могло бы остановить уже обновлённое приложение при ошибке Grafana.

Изменение плана: предложен `ansible/tasks/monitoring.yml` после успешного release task, вне обработчика неудачного выпуска. Повтор мониторинга не должен выполнять выпуск приложения заново. Ansible/CD сообщает ошибку мониторинга, сохраняя работу приложения.

### A3. Смена драйвера и non-blocking-режим не были необходимы для SSH-доступа

Место первой редакции: обязательные `local`, `mode=non-blocking`, `max-buffer-size` в таблице хранения. Источник: Compose не задаёт logging options; настройки Docker daemon сервера неизвестны.

Проверка: сопоставлены Compose и официальная документация Docker о logging drivers и доставке сообщений. Наблюдение: ротацию можно настроить для `json-file` и `local`; доступ через Docker CLI не требует смены драйвера. Non-blocking сознательно допускает потерю сообщений при заполнении буфера.

Последствие: лишняя миграция формата локальных логов и изменение поведения при перегрузке без заявленного требования. Отсутствие настроек в Compose не доказывает отсутствие ротации на сервере.

Изменение плана: сначала выяснить фактический драйвер, сохранить подходящий драйвер и режим, настроить ограниченную ротацию. Non-blocking оставить отдельным решением с явным выбором между обратным давлением и потерей сообщений. Пересоздание контейнера и потеря его старой локальной истории по-прежнему учитываются.

### A4. Описание пересоздания activity-logger/MongoDB было неточным

Место первой редакции: утверждение, что release-скрипт не гарантирует обновления работающих activity-logger/баз. Источник: `scripts/deploy_release.py:108`, `:132`.

Проверка: прочитаны реальные команды и сопоставлены с документированным `compose up`. Наблюдение: `up -d mongo activity-logger` пересоздаёт контейнеры при изменении конфигурации/образа; это отличается от `postgres`, который стартует с `--no-recreate`.

Последствие: из прежнего описания мог следовать ненужный отдельный force-recreate activity-logger/MongoDB. При ротации их логи всё равно могут потеряться, но механизм обновления уже существует.

Изменение плана: разделены обычное обновление activity-logger/MongoDB и отдельное обслуживание PostgreSQL; лишний принудительный перезапуск не требуется. Контейнеры в рамках аудита не запускались, гарантия относится к прочитанным командам и семантике Compose.

### A5. Для последующих Compose-задач не был определён полный контекст выпуска

Место первой редакции: запуск отдельного сценария после выпуска, файл секрета Grafana, общий Compose. Источники: `ansible/deploy.yml`, обязательная интерполяция `IMAGE_BASE`/`IMAGE_TAG` в `docker-compose.yml`, `scripts/deploy_release.py:21–23`.

Проверка: прослежены источники environment Ansible и аргументы Compose. Наблюдение: `IMAGE_BASE` и `IMAGE_TAG` передаются существующей задаче выпуска через её `environment`. Это не записывает их в `.env` и не наследуется следующей задачей. Явное имя сервиса не исключает разбор остального Compose-файла. Профиль также не следует считать защитой от обязательной интерполяции.

Условие и последствие: если этих значений нет в `.env`, последующая Compose-команда без environment не сможет разобрать конфигурацию, хотя образы приложения ей запускать не требуется. Если добавить обязательную переменную Grafana в общий файл, аналогичный конфликт возможен при выключенном мониторинге. Это анализ будущей интеграции, а не уже воспроизведённый сбой текущего production.

Изменение плана: передавать `image_base`/`release_tag` в каждой Compose-задаче, сохранять имя проекта и абсолютные пути, подготовить секрет до старта Grafana; отдельно проверить выключенный мониторинг без нового секрета. Учтены UID/GID чтения файла. Уточнён смысл флага: false пропускает управление, но не останавливает контейнеры.

### A6. Размер памяти не опирался на проверку состава метрик

Место первой редакции: таблица бюджета Prometheus/Grafana. Источник: `backend/internal/http-server/middleware/metrics/metrics.go:45–60`, подключение middleware в `router/router.go`.

Проверка: прочитан middleware, подключённый в основном router. Наблюдение: при пустом шаблоне маршрута label `path` берётся из полного `r.URL.Path`; различные неизвестные пути способны создавать разные серии. Следовательно, начальные 512 МиБ не являются подтверждённым достаточным лимитом.

Условия: middleware должен обработать запрос без шаблона маршрута; фактический объём зависит от запросов, их ограничения, scraping и хранения. В этом аудите не измерялась нагрузка и не доказывались OOM/отказ сервера.

Изменение плана: добавлена проверка числа серий и расхода ресурсов на ограниченном тестовом наборе до назначения лимитов. Потенциальная нормализация неизвестных путей — отдельное изменение приложения. Также отмечено, что текущий scrape-конфиг не собирает свободный диск VM: нельзя обещать готовый host dashboard/alert без дополнительного источника.

### A7. Критерии готовности и SSH-ролей были сложнее и местами шире результата

Место первой редакции: два forward по умолчанию, обязательная новая SSH-роль, healthcheck внутри образа и проверки отдельного сценария.

Проверка: сопоставлены потребность браузера, текущий SSH/CD и официальные endpoints готовности. Наблюдение: оператору для штатного просмотра достаточно одного Grafana-туннеля; Prometheus нужен только для диагностики. Ansible может проверять HTTP на loopback сервера без curl/wget внутри контейнера. `compose up --wait` без healthcheck означает running, а не корректный scrape.

Изменение плана: на первом этапе используется существующий персональный доступ уполномоченного оператора. Отдельная роль без shell нужна только при делегировании; одного PermitOpen при сохранённом shell недостаточно. Prometheus readiness, Grafana health/database, scrape target и отсутствие анонимного доступа проверяются отдельно. Окончание туннеля не описывается как отзыв Grafana-сессии.

Остаточное условие: это не делает обычную учётную запись администратора ролью только для просмотра. Нельзя выдавать её стороннему наблюдателю как ограниченный доступ.

### A8. Различие метрик и текстовых логов нужно сохранить в критериях результата

Место первой редакции: цель документа, первый этап и следующий этап Loki/Alloy. Проверка: прочитаны Prometheus scrape-конфиг, provisioning Grafana и путь пользовательских событий.

Наблюдение: в репозитории настроен только Prometheus datasource; Loki/сборщик отсутствуют. Создание задачи на подключённом `POST /api/v1/tasks` вызывает `save.New` (`router.go:183`), затем `LogEvent` с `title` (`tasks/save/save.go:160–163`). Клиент сериализует details (`clients/activitylogger/queue.go:76–85`); activity-logger печатает полный payload (`activity-logger/cmd/main.go:42–44`). Это статически подтверждённый путь вывода содержания задачи при успешной доставке события, а не исполненный в аудите тест с MongoDB.

Условие и последствие: при выдаче нового доступа к таким техническим логам наблюдатель может получить текст задач без пользовательских API-ограничений. Это не означает публичную доступность логов: для неё соответствующего доказательства нет.

Решение: сохранить очистку log sites перед расширением круга читателей. Она не требует изменения MongoDB-истории и гарантий доставки. SSH-просмотр не заявлять поиском логов в Grafana; Loki/Alloy остаются явно отдельным расширением. До выбора способа сбора этот раздел не является готовым планом центральной агрегации.

## Что оставлено обязательным, что отложено

Обязательны проверенные loopback bindings и отсутствие публичного reverse proxy, внешний тест IPv4/IPv6, проверенный SSH host key, авторизация Grafana, воспроизводимые образы, ограничение хранения и проверка готовности/scrape. Это непосредственно обеспечивает требуемый доступ и эксплуатацию на общей VM.

Отдельная сеть, новый Python orchestration layer, новый SSH-пользователь/помощник, смена log driver, потеря сообщений как политика по умолчанию и централизованный Loki не являются условиями минимального этапа. Новая сеть и Loki остаются вариантами при дополнительных требованиях. VPN/публичный Grafana через BasicAuth для одного оператора не упрощают имеющийся SSH-путь.
