# Обработка ошибок: второй этап

Дата: 25 октября 2026 года. Основание: этап 2 [плана](API-ERROR-HANDLING-REPORT-2026-10-25.md), [baseline](API-ERROR-BASELINE-2026-10-25.md), [общий рендерер](API-ERROR-RENDERER-2026-10-25.md).

Подключённые обработчики, авторизация, ошибки `Operation` и роутерные 404/405 переведены на `apiresponse.Write`. Код назначается явно, без поиска по сообщению. HTTP-статусы, публичные сообщения, legacy-поля и успешные ответы сохранены. `Errors` остаётся подключённым: rate limit и восстановление после panic относятся к этапу 3, удаление нормализатора — к этапу 4.

## Защита изменений

Пути в таблице относятся к `backend/internal/http-server/`. Общая защита перевода — неизменённые ожидаемые JSON нулевого этапа, повторное исполнение маршрутов без нормализатора и существующие тесты соответствующих пакетов. Baseline не охватывает каждый возможный отказ каждого обработчика; специальные проверки указаны отдельно.

## Согласованность

- Механически заменены 137 простых ветвей записи ошибок; отдельно проверены account, contracts, health, расширенный start/409, helper-адаптеры, Operation и router. В подключённых handler/auth/helper-путях старых сериализаторов ошибок не осталось.
- Общий машинный код выбирается в ветви обработчика, специальные — при распознавании типизированного отказа. Сообщение не выбирает код. Эвристики в старом `Errors` пока сохранены для переходного периода.
- `ContractError.Fields` сохраняются только в семействах, где передавались прежде. Отдельные старые `fail`/`problem` игнорировали их; автоматическое раскрытие дополнительных полей не вводится.
- Прежние не подключённые `auth/register`, `auth/verify`, `stats/update` оставлены. Их наличие не означает, что публичные маршруты используют их ошибки.
- Rate limit, recoverer и webhook не переводились на новый JSON-контракт в этом этапе. Все их исходные сценарии остаются в обычном baseline.
- OpenAPI и frontend не изменены: внешний контракт сохраняется. Их согласование по обязательности/типам полей остаётся на этапе 3. Изменения файлов БД, миграций, зависимостей, окружения и выпуска не требовались.

## Проверки

Целевой запуск из `backend/`:

```powershell
go test -p 1 -race -tags integration ./internal/http-server/router ./internal/http-server/apiresponse ./internal/http-server/handlers/pomodoros/start -run '^TestErrorContract|^TestWrite|^TestFromError|^TestCodeDoesNotDependOnMessage|^TestStart_ConflictActiveSession$' -count=1
```

Результат: успешно. Проверены 65 прежних сценариев + 60 повторных без нормализатора, идентификаторы текущего запроса, рендерер и структурированный start/409. Модульные сценарии с sqlmock не подменяют PostgreSQL: отдельно исполнены 27 + 26 сценариев с настоящей одноразовой БД. Ошибка отсутствующего импорта в промежуточной сборке и устаревший `map[string]string` в тесте active/404 устранены; неуспешные прогоны не засчитаны.

Полный набор запускается согласно [BACKEND-TESTING.md](BACKEND-TESTING.md): `-count=1 -p 1 -race -tags integration -covermode=atomic`, `-coverpkg` всех рабочих пакетов без generated mocks, отдельный игнорируемый профиль `backend/coverage-error-migration-final.out`. Финальный лог — `.workbench/error-baseline-20261025/backend-migration-final.log`.

Первый полный прогон не засчитан: кроме устаревшего тестового DTO, `TestBusinessActions` получил ошибку Testcontainers `reaper ... port endpoint: invalid port` при создании контейнера, до исполнения SQL-сценария. Его лог и профиль сохранены отдельно как `backend-migration.log` и `coverage-error-migration.out`. Настройки Docker и код контейнерных проверок для обхода ошибки не изменялись.

Окончательный полный прогон завершился с кодом 0: все backend-пакеты, настоящий PostgreSQL и `-race` прошли. `TestBusinessActions` включён в успешный пакет postgres; инфраструктурный отказ предыдущего запуска не повторился. Нормализация профиля `go run -p 1 ../scripts/coveragecheck -profile coverage-error-migration-final.out -min 80` прошла: **84,04% — 4356/5183 операторов**, порог 80% достигнут.

Состав изменений сопоставлен с таблицей защиты: все 44 изменённых/добавленных Go-файла этого этапа перечислены. Проверены `gofmt`, `git diff --check`, ссылки документов и отсутствие старых сериализаторов в подключённых путях. Публичные fixtures нулевого этапа не изменялись.

Frontend и остальные Go-модули не менялись; их проверки на этом этапе не запускались. Деплой, письма и настоящие платежи не выполнялись. Результат относится к локальному прогону, а не удалённому CI. Коммитов и PR не создавалось.
