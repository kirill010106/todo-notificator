## Дополнительные сценарии доказательства

### Backend: девять подтверждённых сценариев

Архив исходника: [backend-probes.go.txt](../../.workbench/audit-2026-10-16/backend-probes.go.txt). Использовались реальные router/handlers/storage и отдельная PostgreSQL 16 с миграциями. Платёжный HTTP-провайдер заменён тестовым ответом; реальных списаний нет. Для гонки категорий тестовая обёртка синхронизирует чтения количества, а операции создания идут в настоящую БД.

В ходе запуска наблюдались следующие успешные проверки **текущего ошибочного поведения**:

| Сценарий | Наблюдение |
|---|---|
| proxy_clients_share_the_same_rate_limit | 100 запросов разных forwarded-клиентов расходуют один бюджет; новый клиент получает 429 |
| free_categories_race | Восемь параллельных созданий при двух исходных категориях дают десять категорий Free |
| Local_timezone_persists_but_breaks_rewards | PATCH принимает Local, последующий запрос ежедневных заданий получает ошибку PostgreSQL |
| payment_retry_is_not_idempotent | Один платёж и один ключ: первый ответ 200, повтор 500 |
| unconfigured_payment_finder_panics_for_pending_payment | Nil-указатель внутри интерфейса приводит к panic и HTTP 500 через Recoverer |
| streak_never_expires_on_read | Через десять дней без активности возвращается прежняя текущая серия семь |
| empty_first_device_import_locks_out_real_legacy_rewards | Пустой первый импорт блокирует последующий перенос реальных наград и оформления |
| legacy_reward_with_price_five_is_silently_discarded | Старая допустимая награда за пять монет пропущена, импорт помечен завершённым |
| stale_title_edit_silently_removes_new_reminder | Сохранение названия со старым пустым массивом отменяет добавленное другой вкладкой напоминание |

Это запись наблюдений проверок, а не утверждение, что весь дополнительный набор завершился зелёным. В расширенном запуске первые девять сценариев прошли, а десятый тест восстановления старого платежа имел ошибку настройки тестового клиента. Настройка архивного исходника исправлена; к заключительному повтору Docker уже стал недоступен. Последний [backend-probes.log](../../.workbench/audit-2026-10-16/backend-probes.log) содержит именно этот инфраструктурный отказ. Пункт A06 в основном отчёте поэтому отмечен **«по коду»**, без заявления об успешном воспроизведении десятого сценария.

Для воспроизведения архив временно размещается как `backend/internal/http-server/router/audit_tmp_test.go`; из backend выполняется `go test -p 1 -tags integration ./internal/http-server/router -run '^TestAudit20261016$' -count=1 -v`. После проверки временный файл удаляется. В текущей рабочей копии его нет.

### Frontend: три подтверждённых сценария

Архив исходника: [frontend-probes.test.ts.txt](../../.workbench/audit-2026-10-16/frontend-probes.test.ts.txt). Результат: **3 из 3**, [frontend-probes.log](../../.workbench/audit-2026-10-16/frontend-probes.log).

- Запрос от A после внешней смены токенов на B повторяет старое тело с авторизацией B.
- Выход после обновления access/refresh отправляет старый refresh-токен в теле с новым access-токеном.
- Браузерное форматирование с `timeZone: "Local"` выбрасывает RangeError.

Используются подмена fetch и настоящий код API-клиента. Проверка смены аккаунта моделирует изменение общего хранилища и событие storage; компонентный обработчик сверялся с кодом. Это не запись двух реальных браузерных вкладок. Серверная авторизация чужого пользователя не обходится.

Для повтора архив временно размещается как `frontend/src/lib/audit-tmp.test.ts`, запускается соответствующий файл Vitest и затем удаляется. Не переносить утверждения «дефект присутствует» в постоянный CI: при исправлении нужны противоположные ожидания.

## Предварительные неуспешные запуски

В каталоге сохранены и предварительные журналы. Параллельная компиляция Go получила ошибку недостаточного файла подкачки; параллельный Vitest/Vite — нехватку памяти; браузерные прогоны — потерю сервера/тайм-ауты. Итоговые последовательные штатные прогоны выше прошли. Эти сообщения не зарегистрированы как доказательства дефектов приложения.

Первый activity-logger-прогон не смог запустить отсутствующий MongoDB 6. После загрузки образа повтор прошёл. В конце аудита Docker API снова был недоступен; рабочие сервисы и конфигурация Docker не менялись. Попытка найти стандартный установленный Docker Desktop не дала исполняемого файла, поэтому окончательный дополнительный backend-повтор остался незавершённым.

## Границы

Не было реальной оплаты, реального SMTP, атак на production и нагрузки до исчерпания ресурсов. PostgreSQL/MongoDB создавались отдельно для тестов; production/рабочая база не правилась. Playwright использует тестовые ответы API. `govulncheck` проверял исходники с локальной версией Go, а не финальные Linux-образы. Сканер также выводит библиотечные и отозванные записи; основной отчёт оценивает применимость и не считает каждую строку отдельной уязвимостью.
