Дата: 21 октября 2026 года. База изменений — HEAD `b2be50e`, включающий исправления P1 из `2ffb4fa`. Проверена рабочая копия с описанными ниже изменениями. Номера сохранены из [повторного аудита](SECURITY-RECHECK-2026-10-20.md).

Исправлены все пять подтверждённых P2: №3, №5, №6, №7, №11. P3 №8–10 не исправлялись. Миграции, зависимости, сгенерированный protobuf, настройки инфраструктуры и IP-фильтр платежей не менялись. Деплой, реальные платежи и отправка писем не выполнялись.

## Исправления и последовательные проверки

### №3. Ограничение login и refresh

Места: [общий декодер](../backend/internal/http-server/helpers/json.go), [login](../backend/internal/http-server/handlers/auth/login/login.go), [refresh](../backend/internal/http-server/handlers/auth/refresh/refresh.go).

До исправления публичные обработчики читали многомегабайтное тело до проверки учётных данных. Теперь весь JSON, включая неизвестные поля и завершающие пробелы, ограничен 4096 байт через `http.MaxBytesReader` до декодирования. Превышение даёт `413 PAYLOAD_TOO_LARGE`; второй JSON-документ и некорректный ввод — `400`. Email ограничен 254 символами, пароль — 72 байтами UTF-8, refresh-токен — 64 байтами. Эти границы согласованы с регистрацией и форматом выдаваемого случайного токена.

Проверки: `helpers/json_test.go`, `login/limits_test.go`, `refresh/limits_test.go`, `router/auth_limits_test.go`. Поток неизвестной длины с 8 МиБ данных читает не более **4097 байт**; тело ровно 4096 байт принимается декодером. Недопустимые поля, Unicode-переполнение и лишний JSON отвергаются до обращения к хранилищу. Реальный подключённый роутер возвращает `413`. Пакеты авторизации, helpers и router проверены с `-race`; успешные HTTP-потоки дополнительно входят в PostgreSQL-интеграцию P1.

Аудит согласованности: ротация и отзыв токенов остались в существующих атомарных операциях, сравнение пароля и проверка аккаунта не обходятся. Ограничение размера не зависит от прокси или `Content-Length`. OpenAPI обновлён. Это устраняет доказанное неограниченное чтение; абсолютная устойчивость к любой нагрузке не заявляется.

### №5. Ротация между вкладками

Место: [api.ts](../frontend/src/lib/api.ts). Общая для origin эксклюзивная Web Lock `todo-notificator:refresh` сериализует ротацию. После получения блокировки вкладка повторно читает токены: если предыдущая вкладка уже обновила ту же учётную запись, новый запрос не отправляется. Ожидание и запрос ограничены общим сроком 15 секунд. Старый ответ после logout/смены пользователя не возвращает токены и данные прежнего аккаунта; запоздалый `401` не удаляет более новую ротацию.

Проверки: [модульные сценарии](../frontend/src/lib/api.test.ts) и [два реальных Chromium-tab](../frontend/e2e/session-refresh.spec.ts). Для каждого из двух лидеров второй tab поставлен в очередь настоящего LockManager до завершения первого ответа: оба завершаются успешно, выполняется ровно один POST refresh. Ещё два браузерных теста проверяют logout и смену аккаунта при двух ожидающих вкладках. Модульные тесты проверяют transient failure, отсутствие Web Locks, запоздалый `401`, декодирование старого ответа, повтор logout с новым токеном и объединение запросов внутри вкладки.

Аудит согласованности: координация не доверяет одному флагу в `localStorage`, не требует таймера аренды и освобождается браузером при завершении callback. Принятие обновлённых токенов разрешено только для известной той же identity. Механизм требует HTTPS в production и браузер с Web Locks; без API клиент завершает сессию и требует повторного входа. Потеря ответа после уже выполненной серверной ротации по-прежнему может потребовать входа. Требования и гарантии API: [MDN Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API); ограничения клиента отражены в [FRONTEND.md](FRONTEND.md).

### №6. Граница страницы и объёма истории

Места: [HTTP-обработчик](../backend/internal/http-server/handlers/logs/get/get.go), [gRPC-сервис](../activity-logger/cmd/main.go), [общие лимиты](../pkg/activitylog/limits.go).

Страница по умолчанию — 50, максимум — 100 записей. Ограничение применяется до вызова gRPC и перед формированием MongoDB `find`, включая прямой gRPC-вызов. Для Free сохранены максимум 5 и offset=0; актуальный тариф поступает из middleware с чтением пользователя в БД. Перед добавлением записи в результат вычисляется размер protobuf; свыше 4 МиБ возвращается `ResourceExhausted` без успешной частичной страницы. HTTP преобразует такую ошибку в общий `500` без деталей БД.

Проверки: `logs/get/limits_test.go`, `activity-logger/cmd/logs_security_test.go` и дополнение `TestServerIntegration`. Проверены крайние/невалидные значения HTTP и gRPC, фактическая команда MongoDB-драйвера с limit=100. На одноразовой настоящей MongoDB 150 записей читаются страницами 100+50; две записи примерно по 2 МиБ дают ошибку, одна читается успешно. Пакеты проверены с `-race`.

Аудит согласованности: фильтр владельца сохранён; protobuf wire-контракт не изменился, добавлен только комментарий в `.proto`. Размер ограничен по сериализованному protobuf, а не по JSON HTTP-ответа и не по всей памяти драйвера. Глубокий offset всё ещё может требовать дорогого сканирования; переход на cursor pagination и индексы требует отдельной задачи. OOM не моделировался и не утверждается.

### №7. Ошибки чтения истории

Место: [GetLogs](../activity-logger/cmd/main.go). Ошибка `Decode` немедленно завершает запрос; после цикла проверяется `cursor.Err()`. Ошибка начального `Find`, декодирования либо следующей порции возвращается как gRPC `Internal` без частичных данных и внутренних диагностических строк.

Проверки `TestGetLogsRejectsPartialHistoryOnCursorFailure` и `TestGetLogsRejectsPartialHistoryOnDecodeFailure`: настоящему MongoDB-драйверу через его штатный mock deployment передаются успешная первая запись, затем отказ `getMore` с кодом 43 или несовместимый BSON. В обоих случаях результат `nil`, ошибка `Internal`; приватная диагностическая строка отсутствует в ответе. Полная и пустая выборки остаются успешными. Это инъекция ошибки драйвера, а не имитация отказа настоящего MongoDB-сервера. Успешная интеграция с настоящей MongoDB проверена отдельно в предыдущем шаге.

Аудит согласованности: HTTP-клиент передаёт ошибку без выдачи успешного обрезанного списка. Гарантии best-effort записи событий не расширялись. Существующие `context.Background()` и таймаут 5 секунд не менялись: отмена входящего контекста — отдельный P3 №8.

### №11. Проверка отмены и финальные состояния платежей

Места: [webhook](../backend/internal/http-server/handlers/payments/webhook/webhook.go), [sync](../backend/internal/http-server/handlers/payments/sync/sync.go), [PostgreSQL](../backend/internal/storage/postgres/payment.go).

Webhook для `payment.canceled` и `payment.succeeded` обязательно запрашивает API провайдера и сверяет **ID и статус**. Sync также отвергает чужой ID в ответе провайдера. SQL разрешает переход из pending/waiting_for_capture в финальный статус либо повтор того же финального статуса. Succeeded и canceled не переходят друг в друга. Повтор сохраняет `updated_at`; успешная оплата и boolean Premium по-прежнему фиксируются одной транзакцией. Общий `UpdatePaymentStatus` принимает только отмену, чтобы обойти атомарную выдачу Premium через него было нельзя.

Проверки: `webhook/security_test.go`, `sync/failures_test.go`, `payment_transition_test.go`, `payment_atomic_test.go`, [TestPaymentTerminalSecurityIntegration](../backend/internal/storage/postgres/payment_security_integration_test.go). Проверены отказ/пустой ответ API, несовпадающие ID/статусы, нулевые обращения к updater при неподтверждённом событии, повторы и обе очередности финальных событий. На одноразовом PostgreSQL 16 проверены 16 конкурентных переходов: восемь одинаковых разрешены, восемь противоположных дают конфликт, статус согласован с Premium. Искусственная ошибка UPDATE пользователя через PostgreSQL-trigger откатывает изменение статуса и даёт webhook `500`.

При конфликте уже сохранённого финального статуса webhook пишет предупреждение и отвечает `200`, сохраняя данные. Отсутствующая локальная запись или временная ошибка возвращает `5xx` для повторной доставки: внешний платёж может быть создан раньше локальной записи. SQLmock отдельно проверяет вставку записи между условным UPDATE и чтением причины отказа: событие остаётся повторяемым, а не ошибочно подтверждённым. Исторические противоречивые записи не исправляются автоматически и требуют отдельной сверки с провайдером.

Аудит согласованности: сохранены IP-фильтр, проверка владельца/суммы/валюты при UPSERT, изоляция ключа идемпотентности по пользователю и атомарность Premium. Возврат средств не является сменой succeeded → canceled и этим обработчиком не реализуется. Неизменность терминальных статусов следует [процессу платежа YooKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process); поведение `200`/повторов согласовано с [протоколом уведомлений](https://yookassa.ru/developers/using-api/webhooks). Проверки используют заглушку API, реальных запросов/платежей не было.

### Аудит Go-зависимостей и окружения

Выполнен `govulncheck` для `./backend/... ./activity-logger/... ./pkg/...` и того же набора в отдельном архиве HEAD `b2be50e`. С локальным Go 1.27.1 оба сканирования дали одинаковые **12 symbol-level предупреждений**, новых ID — **0**. Пять package-level и одно module-level предупреждение без обнаруженного вызова не объявляются воспроизведёнными дефектами.

Одиннадцать symbol-level предупреждений относятся к стандартной библиотеке Go 1.27.1: `GO-2026-6599`, `6600`, `6603`, `6605`, `6607`, `6608`, `6610`, `6611`, `6612`, `6613`, `6617` (у всех полный префикс `GO-2026-`). Сканер указывает исправление в Go 1.27.2; эта версия уже закреплена в CI и Dockerfile backend/activity-logger. Это не проверка версии работающих production-бинарников. Локальные проверки на Go 1.27.1 не следует трактовать как чистый результат сканирования.

Отдельный повтор с `GOTOOLCHAIN=go1.27.2` подтвердил отсутствие этих одиннадцати symbol-level предупреждений. Осталось одно symbol-level предупреждение gRPC, а также три package-level и одно module-level без найденного вызова. **Govulncheck не завершился с чистым статусом**; оставшийся результат разобран ниже.

Оставшееся предупреждение — [GO-2026-6443](https://pkg.go.dev/vuln/GO-2026-6443) для gRPC 1.83.1. [Advisory разработчиков](https://github.com/grpc/grpc-go/security/advisories/GHSA-2v4p-qf9q-27wj) требует `xds.NewGRPCServer()` с xDS routing interceptor. Текущий `activity-logger/cmd/main.go` создаёт обычный `grpc.NewServer()`; xDS в затронутых модулях не подключён. Условие падения из advisory в проверенной конфигурации не установлено, поэтому это предупреждение зависимости не добавлено к подтверждённым P2. Обновление gRPC следует учитывать при отдельном обслуживании зависимостей; переход на xDS до него требует повторной проверки.

Зависимости и release toolchain в этом наборе исправлений не изменялись. Сравнение одинакового набора ID подтверждает отсутствие новых предупреждений сканера, а не отсутствие любых новых уязвимостей. Дополнительно вручную проверены границы данных, владельцы, очистка сессии, SQL-переходы, откат, обработка ошибок и ответы API, описанные выше.

Проверены изменённые пути и их регрессии. Прохождение тестов и сканеров не является доказательством отсутствия любых уязвимостей или подтверждением состояния production. Непроверенные реальные интеграции — платёжный API, SMTP и рабочая инфраструктура.
