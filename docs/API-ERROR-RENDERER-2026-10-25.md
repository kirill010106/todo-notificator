# Обработка ошибок: первый этап

Дата: 25 октября 2026 года. Основание: этап 1 [плана](API-ERROR-HANDLING-REPORT-2026-10-25.md) и [baseline нулевого этапа](API-ERROR-BASELINE-2026-10-25.md).

Добавлен самостоятельный JSON-рендерер ошибок. Подключение к обработчикам начинается на втором этапе согласно таблице плана. Текущие маршруты, `Errors`, `Operation`, транзакции и webhook продолжают работать прежним способом. На этом этапе уменьшение буферизации или ускорение запросов не заявляется.

## Согласованность и ограничения

- Непустой `request_id` обеспечивается существующим middleware `RequestID`, который должен предшествовать вызову `Write`. Рендерер не создаёт второй идентификатор.
- HTTP-статус, код и публичное сообщение передаёт вызывающая сторона. `Write` предназначен для записи до начала ответа; он не восстанавливает уже отправленные заголовки и не перехватывает panic.
- `ContractError.Message` считается публичным по существующему контракту. Адаптер не скрывает произвольные сообщения, ошибочно помещённые в этот тип; безопасный fallback применяется к остальным ошибкам.
- Журналирование остаётся в месте обработки исходной причины. Рендерер не журналирует повторно и не получает тело запроса или секреты.
- `Response.Status` имеет тип `any` только ради существующих JSON-вариантов. `Write` задаёт строку `Error`, HTTP-число либо пропускает поле согласно `StatusStyle`.
- Сравнение 52 форм доказывает возможности сериализации. Оно само по себе не проверяет преобразование ошибки конкретным обработчиком, PostgreSQL или провайдера. Эти уровни различаются с исполнением 65 сценариев настоящего роутера.
- Baseline-файлы не обновлялись под новый код. OpenAPI и frontend не менялись: ни один маршрут ещё не использует рендерер, а наблюдаемый API сохраняется. Прежние расхождения OpenAPI с вариантами `status`/null согласуются на этапе 3.
- Начальный каталог содержит общие коды, коды лимитов категорий/перерывов/напоминаний и команд. Полный перенос строковых литералов из domain и хранилища не входит в этап 1; зависимости направлены из HTTP-пакета к domain.

## Проверки

Целевая проверка из `backend/`:

```powershell
go test -p 1 -race -cover ./internal/http-server/apiresponse -count=1
```

Результат: успешно, покрытие нового пакета **100%**. Первоначальный запуск в sandbox получил отказ при записи временного покрытия и не засчитан как успешный; повторный обычный запуск завершился с кодом 0.

Полный backend-набор выполняется по [BACKEND-TESTING.md](BACKEND-TESTING.md) с `-count=1 -p 1 -race -tags integration -covermode=atomic`, `-coverpkg` всех рабочих пакетов без сгенерированных mocks. Используются отдельные игнорируемые файлы `backend/coverage-error-renderer.out` и `.workbench/error-baseline-20261025/backend-renderer.log`.

Результаты полного прогона:

- Все backend-пакеты прошли, код завершения 0. Исполнены 65 сценариев baseline настоящего роутера, отдельная проверка request_id и существующие интеграции, включая миграции, откаты и конкурентные команды с PostgreSQL 16.
- `go run -p 1 ../scripts/coveragecheck -profile coverage-error-renderer.out -min 80` прошёл: **83,68% — 4472/5344 операторов**, требуемые 80% достигнуты. Покрытие нового пакета отдельно — 100%; оно не подменяет общий показатель.
- Форматирование `gofmt`, `git diff --check` и ссылки двух затронутых документов проверены. Все 17 констант уникальны и совпадают с существующими значениями в исходниках; импортов нового пакета в действующих обработчиках нет.
- Frontend и остальные Go-модули не менялись, их проверки повторно не запускались. Деплой, настоящие платежи и отправка писем не выполнялись; PostgreSQL использовался в одноразовых Docker-контейнерах. Результат относится к локальному запуску, а не удалённому CI.

Следующее изменение по плану — перевод категорий и pause на общий рендерер с явными специальными кодами. Существующий `Errors` сохраняется до завершения остальных этапов.
