# Стоит ли переходить к чистой архитектуре

Дата: 21.10.2026. Основание: рабочая копия на HEAD `6c32fb8`.
Статус: анализ и предложение; рефакторинг не выполнен и не согласован к реализации.

## Решение

**Имеет смысл постепенно выделить бизнес-правила и слой сценариев в backend. Полная переделка всего проекта ради «истинной чистой архитектуры» сейчас не выглядит оправданной.**

Главная проблема — смешение обязанностей. Пакет `storage/postgres` одновременно хранит данные, выбирает награды, управляет сценариями и собирает HTTP-ответы. Часть обработчиков напрямую зависит от конкретного PostgreSQL-хранилища. Простое перемещение SQL в другие файлы или добавление слоя, который только пересылает вызовы, эту проблему не решит.

При этом SQL сам по себе не является архитектурным недостатком. Внешние ключи, уникальность, условные UPDATE, блокировки и транзакции защищают действующие гарантии проекта. Убирать их ради переноса всей логики в Go не следует. Продуктовые решения полезно выразить в Go; применение решения к конкурентным данным должно оставаться атомарным в БД.

Практический первый шаг — ограниченный пилот на правилах магазина, **3–6 человеко-дней вместе с фиксацией исходного поведения и проверкой**. Существенное разделение backend оценивается в **17–32 человеко-дня**, строгий вариант с переносом правил из триггеров и полным разделением моделей — ориентировочно в **35–60 человеко-дней**. Это инженерные диапазоны при описанных ниже предпосылках, а не обещание срока. Решение о продолжении стоит принимать после пилота.

По текущему коду нельзя подтвердить, что проект раньше соответствовал чистой архитектуре. Точнее говорить о переходе к ней, а не о восстановлении прежнего состояния.

## Что здесь означает чистая архитектура

Критерий — направление зависимостей: правила и сценарии не должны знать о chi, `http.ResponseWriter`, SQL-транзакциях, MongoDB или SDK YooKassa. Адаптеры реализуют интерфейсы, необходимые сценариям. Важна возможность проверять правила без сервера и БД; количество каталогов вторично. Это соответствует исходному описанию [The Clean Architecture, Robert C. Martin](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html).

Для этого проекта достаточно четырех обязанностей:

| Область | За что отвечает |
|---|---|
| Домен | Решения: положена ли награда, сколько XP, допустим ли переход, как меняется серия дней и цикл фокуса |
| Сценарии приложения | Загрузка актуального состояния, выбор правил, общая транзакция, идемпотентность, согласование изменений |
| Адаптеры | HTTP/JSON, SQL, JWT/bcrypt, YooKassa, gRPC, SMTP; преобразование ошибок и данных |
| Сборка приложения | Создание реализаций и связывание зависимостей в `cmd`/router |

SQL остается в PostgreSQL-адаптере. Чистый домен не требует ORM, отдельного сервиса на каждую сущность, event sourcing или замены PostgreSQL. Отсутствие SQL-импорта в домене само по себе тоже недостаточно: правило, спрятанное в триггере, все равно нельзя проверить отдельно от БД.

## Целевая граница и пример переноса

Предлагаемое направление импортов:

```text
HTTP-адаптер ───────────────> application ──────────> domain
PostgreSQL-адаптер ─────────> интерфейсы application
YooKassa/JWT/gRPC-адаптеры ─> интерфейсы application
cmd/router связывает реализации с интерфейсами
```

Стрелки показывают зависимость исходного кода. Во время выполнения сценарий вызывает PostgreSQL через интерфейс. Возможные каталоги — `internal/application/{tasks,focus,rewards,account,payments}` и существующие `internal/domain`, `internal/storage/postgres`, `internal/http-server`; обязательного переименования всех пакетов нет.

Для завершения задачи поток должен стать таким:

1. HTTP проверяет размер/форму запроса, извлекает пользователя, ключ и явные поля patch; вызывает типизированную команду. Семантика отсутствующего поля, `null` и пустого массива сохраняется.
2. Сценарий через транзакционный порт начинает операцию; PostgreSQL блокирует пользователя, затем нужные задачи/сессии в согласованном порядке. Проверяются права и актуальное состояние из БД.
3. В той же транзакции проверяется replay. Совпадающий запрос получает прежний результат, несовпадающий с тем же ключом — прежний конфликт. Правила канонизации тела и идентификации команды меняются только с планом совместимости.
4. Правила получают заблокированное состояние и выбранное серверное время. Они решают, положены ли XP/монеты, как меняются статус, статистика, бустер и достижения.
5. Адаптер применяет изменения и сохраняет результат идемпотентной операции. При ошибке любого промежуточного шага откатывается все. Результат должен быть готов к сохранению до commit, включая ошибки его преобразования.
6. После commit выполняются предусмотренные best-effort побочные действия. HTTP возвращает совместимое представление результата.

Транзакционный порт должен передавать в callback набор репозиториев, связанных с **одной** транзакцией; `*sql.Tx` не выходит в приложение. Не следует делать отдельную транзакцию в каждом репозитории. Небольшой `UserActionTx`/`WithinUserAction` с явными методами предпочтительнее универсального репозитория для любой таблицы. Порядок блокировок задается контрактом, реализуется PostgreSQL и проверяется интеграцией.

Сейчас транзакция и изменяемый `ActionOutcome` неявно передаются через context. При переходе стоит явно передавать транзакционный набор и возвращать результат из сценария. Context остается для отмены и срока выполнения. Временная совместимость со старым механизмом допустима внутри адаптера, но два независимых механизма commit для одной команды недопустимы.

Особая цена перехода — replay. Таблица `api_operations` уже хранит JSON успешного HTTP-ответа и статус. Нельзя просто сменить формат на новую структуру и потерять старые ответы. На переходном этапе допустим небольшой адаптер старого формата: он сохраняет прежнюю семантику и ошибки сериализации внутри общей операции, но не определяет награды. Далее возможен версионируемый результат с явным преобразованием. Выбор формата нужно принять до замены `ExecuteOperation`; это часть оценки, а не готовое решение схемы.

Источники времени также нельзя унифицировать механически. Сейчас используются и транзакционное `CURRENT_TIMESTAMP`, и фактическое `clock_timestamp()` — например, для окна отмены фокуса. Простая замена всех вызовов на `time.Now()` изменит поведение при ожидании блокировки. Нужно явно определить время каждого решения, сохранить семантику локального дня, DST и границы 24 минут/30 секунд. Для доменного теста время передается значением; в рабочем сценарии его источник выбирается осознанно.

## Варианты и затраты

Оценка предполагает одного разработчика, знакомого с Go/PostgreSQL и проектом, сохранение текущего API и схемы на ранних этапах, доступный Docker для одноразовых интеграционных БД. Человеко-день — день сосредоточенной разработки с проверкой и документацией. Сроки не получены из фактического пилота; уверенность средняя для выделения функций и низкая для полной миграции сценариев и триггеров.

| Вариант | Объем | Оценка | Когда выбирать |
|---|---|---|---|
| Оставить текущую архитектуру | Документировать правила, при новых функциях избегать дополнительного смешения | Нет отдельного проекта рефакторинга; долг сохраняется | Приложение в режиме сопровождения, ближайшие изменения небольшие |
| Пилот | Зафиксировать поведение и выделить правила магазина, сохранив SQL, API, транзакции и триггеры | 3–6 человеко-дней | Рекомендуемый следующий шаг перед большим обязательством |
| Постепенное разделение backend | Правила, слой сценариев, типизированные результаты, небольшие порты; существующие БД-гарантии и триггеры сохраняются как явные исключения | 17–32 человеко-дня, включая пилот; примерно 4–7 рабочих недель с округлением | Если предстоит менять фокус, награды, тарифы и аккаунт |
| Строгое разделение backend | Предыдущее плюс перенос прикладных триггеров, завершение разделения DTO, устранение оставшихся неявных записей и всех обходов сценариев | 35–60 человеко-дней суммарно, примерно 7–12 рабочих недель | Если нужна независимость правил от БД во всех потоках и ее польза подтверждена |

Это не оценка полной переделки монорепозитория. Перестройка frontend, отдельного журнала и всех email-workers в диапазон backend не включена; для нее нужна отдельная декомпозиция. Также не включены новые гарантии доставки, смена схемы кошелька, замена провайдера, новые тарифы, визуальная переделка, выпуск и работа с production-данными. Если потребуется менять поведение вместе с архитектурой, оценки нужно пересчитать.

Разложение рекомендуемого варианта, без параллельного сложения работ:

| Этап | Результат | Человеко-дни |
|---|---|---:|
| 0 | Матрица действующих правил/писателей, baseline относящихся тестов, контракт пилота | 1–2 |
| 1 | Правила магазина вне PostgreSQL-пакета; прежняя транзакция и HTTP | 2–4 |
| 2 | Типизированный исполнитель команд и совместимый replay; один вертикальный сценарий без запуска HTTP из хранилища | 4–7 |
| 3 | Задачи, Pomodoro, XP, стрик, достижения и дневные награды; согласование правил команд и чтений | 5–9 |
| 4 | Сценарии аккаунта/платежей, порты криптографии и провайдера; перенос оставшейся оркестрации HTTP | 3–6 |
| 5 | Проверка границ импортов, интеграционные регрессии и документация исключений | 2–4 |
| **Итого** | **С сохранением трех триггеров и оптимизированных SQL-чтений** | **17–32** |

Основная неопределенность — этапы 2–3: общий исполнитель обслуживает много маршрутов, а состояние задачи, фокуса, наград и replay связано одной транзакцией. Полный перенос триггеров дополнительно требует карты всех записей и плана совместимого изменения схемы. Календарный срок увеличится при параллельных продуктовых работах и ревью; удвоение числа разработчиков не делит его автоматически пополам.

## Как сделать пилот и решить, продолжать ли

Магазин подходит лучше платежей или аккаунта: в `ShopAction` уже видны входное состояние, каталог, действие и итоговый кошелек. Есть интеграционные сценарии конкурирующих покупок и расходования бустера. Пилот должен отделить решение, а не создать еще один метод, который вызывает прежний `Storage.ShopAction`.

В пилоте правило получает кошелек, каталог, команду и необходимые заранее выделенные ID; возвращает новое состояние и сведения о списании либо предметную ошибку. Генерация ID и SQL-запись остаются снаружи. Изменяемые map/slice нельзя случайно разделять между старым и новым состоянием: чистота функции проверяется также на отказе операции. Начальные 50 монет, цены, предел личных наград и запрет импорта браузерных монет сохраняются.

Критерии завершения пилота:

- Решения о покупке, импорте и активации бустера проверяются без PostgreSQL и HTTP; PostgreSQL-код отвечает за чтение и атомарное применение решения.
- Отказ записи ledger или кошелька откатывает обе части. Параллельные покупки не позволяют потратить баланс дважды; replay не повторяет списание.
- Сохраняются HTTP-ответы и поведение клиента, включая повтор неизвестного исхода команды. Существующий исполнитель операций на этом шаге еще допустим.
- Зафиксированы фактические трудозатраты и опыт одного пробного изменения правила. Если правило по-прежнему нужно независимо исправлять в нескольких слоях, пилот не достиг цели.

Продолжать стоит, если следующие функции затрагивают эти правила, новая граница позволяет менять их отдельно и не требует непропорциональной обвязки. Если продукт стабилен и основная работа — эксплуатация или интерфейс, можно остановиться после пилота. Сокращение времени будущих изменений нельзя честно выразить процентом до измерения.

Нельзя временно начислять/регистрировать действие дважды и рассчитывать, что любая уникальность автоматически решит все различия, особенно около смены дня. На пилоте миграции не требуются.

## Что не следует включать в эту работу автоматически

- Введение микросервисов или разделение базы по сущностям. Пользовательские транзакции сейчас объединяют задачу, фокус и награды; разрыв добавит отдельную проблему согласованности.
- Вынос сетевого вызова YooKassa внутрь общей пользовательской транзакции. Сейчас создание платежа намеренно идет вне игрового исполнителя; эту границу нужно сохранить.
- Удаление FK, уникальных ключей, условных UPDATE и SKIP LOCKED. Независимость домена не делает данные защищенными от конкурентной записи.
- Переписывание всех чтений на загрузку сущностей и расчет в Go. Today, пагинация, агрегаты достижений и выборка напоминаний должны сохранять работу на стороне БД и согласованные snapshots.
- Немедленное выделение полной чистой архитектуры в activity-logger. Сервис сравнительно прост и сейчас напрямую соединяет gRPC и MongoDB; вводить порты полезно по мере усложнения сценариев, а не ради симметрии backend.
- Полная переделка email-подсистемы: scheduler уже использует интерфейсы. Общая схема с backend и leases создают отдельный контракт, который нельзя устранить переименованием пакетов.
- Новая надежная доставка журнала через outbox. After-commit callback и отправка журнала остаются best-effort; новая гарантия требует отдельного решения. Outbox подтверждения/восстановления email не превращает в надежный outbox журнал активности.
- Массовое удаление старых методов только по имени или TODO. Например, старый `handlers/auth/register` не определяет текущую регистрацию; подключение и остальные вызовы нужно проверять отдельно.

## Рекомендуемое решение для проекта

Принять постепенное разделение backend как направление для новых изменений, но начать только с ограниченного пилота. Сначала отделить решения, затем оркестрацию и формат ответа; триггеры и механизмы БД на ранних этапах сохранить и описать как явные исключения. После каждого этапа должен оставаться работоспособный, совместимый продукт с проверенными транзакционными гарантиями.

Главная ожидаемая польза — возможность менять правила фокуса, магазина и наград отдельно от SQL и HTTP. Если ради очередного изменения все еще приходится разбирать транзакцию, JSON middleware и триггер одновременно, добавленные слои не принесли требуемого результата. Полную независимость всех потоков от БД имеет смысл оплачивать только после подтверждения этой пользы на небольшом участке.
