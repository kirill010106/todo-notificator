# Исправления только P1 — 20.10.2026

Исправлены два пункта P1 из [повторного аудита](SECURITY-RECHECK-2026-10-20.md). Код пунктов P2/P3 не изменялся. Миграции на рабочей БД и деплой не выполнялись.

## №1: открытые refresh-токены

Все операции хранилища используют SHA-256 исходного случайного токена и колонку `token_hash`: регистрация, вход, смена credentials, ротация, чтение и logout. Поиска по открытому значению и переходного plaintext fallback нет. Полученный из БД хеш нельзя использовать ни для refresh, ни для отзыва исходного токена. Поле хеша исключено из JSON; браузерный API по-прежнему получает исходный случайный bearer-токен.

Миграция `00026_hash_refresh_tokens.sql` отзывает прежние refresh-сессии и переименовывает колонку. Старые сессии не переносятся, чтобы токены из ранее прочитанных записей/бэкапов перестали работать. Up/Down сохраняют пользователей, пароли и outbox; оба направления отзывают сессии. Access JWT остаются действительны до своего срока истечения. Порядок выпуска и ограничения отката описаны в [DEPLOYMENT.md](DEPLOYMENT.md).

После первого исправления проверены:

- Модульные backend-тесты; два теста локальных webhook, заблокированные sandbox, успешно повторены с разрешённым loopback.
- `TestFrontendContracts`: все 16 существующих сценариев, включая атомарность, права, платежи, фокус, аккаунт и конкурентную ротацию.
- Новый `TestRefreshTokenSecurityIntegration`: настоящие HTTP register/login/refresh/logout, смена/восстановление пароля, запрет replay хеша, единственный победитель из восьми ротаций, отзыв прежних сессий и Up/Down схемы 25 → 26.
- Оба интеграционных набора запущены с `-race` на двух пустых одноразовых PostgreSQL 18 БД. Для существующего набора временный Go overlay заменил только запуск Docker на подключение к отдельной тестовой БД; его проверки не менялись. Кластер после прогона остановлен.

Сохранены порядок блокировок пользователя/токенов, проверка `auth_version`, условия срока действия в UTC и атомарность account-операций. Публичный HTTP-контракт не менялся.

## №2: доверие сетевому SSH host key

CD больше не получает ключ через `ssh-keyscan`. `scripts/configure_deploy_ssh.py` связывает заранее проверенный `SSH_HOST_PUBLIC_KEY` с точным `SERVER_IP`, проверяет формат через `ssh-keygen` и атомарно создаёт отдельный known_hosts. Ошибочная настройка не заменяет прежний файл; отсутствие ключа останавливает job до загрузки приватного ключа и создания production `.env`.

У Ansible включён `ANSIBLE_HOST_KEY_CHECKING=True`; OpenSSH использует `StrictHostKeyChecking=yes` и только заданный файл. Альтернативные global known_hosts, автоматическое добавление ключей и доверие DNS SSHFP отключены. Подмена ключа не превращается в автоматическое обновление доверия.

Проверки второго исправления:

- 4 Python-теста: точная привязка IPv4/IPv6/DNS, отклонение некорректных ключей/хостов без перезаписи доверия, отказ при отсутствии секрета и настройки workflow. Тесты добавлены в CI.
- `TestDeploymentRejectsSubstitutedHostKey`: настоящий OpenSSH-клиент и две локальные SSH-заглушки. Проверенный ключ допускается, иной ключ отвергается до аутентификации. Реальные пользовательские SSH-credentials не используются.
- Тесты выпуска: 16 прошли, 2 контейнерных пропущены из-за недоступного Docker; все 6 проверок production-конфигурации прошли.
- YAML обоих workflow и Ansible playbook успешно разобран. Локальный Ansible CLI отсутствует (`ansible.cli` недоступен); существующая проверка `ansible-playbook --syntax-check` остаётся в Linux CI. Удалённый CI в этой задаче не запускался.

Перед следующим CD **нужно добавить GitHub Actions secret `SSH_HOST_PUBLIC_KEY`**: одну проверенную через доверенную консоль строку публичного host key сервера. Имеющиеся `SSH_PRIVATE_KEY`, `SERVER_IP`, `SERVER_USER`/`SSH_USER`, `PROD_ENV_FILE` его не заменяют. Ключ сервера нельзя получить из пользовательского приватного ключа. Секреты GitHub в этой задаче не создавались; до настройки нового секрета deploy job безопасно остановится.
