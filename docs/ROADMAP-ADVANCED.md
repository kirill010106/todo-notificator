# Состояние проекта и план развития

Актуализировано 15 октября 2026 года по текущему коду. Это рабочий список оставшихся задач, а не отчет о проверке production. Правила API находятся в [OpenAPI](openapi.yaml), начисления — в [BUSINESS-LOGIC.md](BUSINESS-LOGIC.md), устройство клиента — в [FRONTEND.md](FRONTEND.md).

## Что уже реализовано

- Один React + TypeScript + Vite клиент в `frontend/`; прежние Alpine.js и альтернативный React-клиент удалены. Есть адаптивная навигация, две темы, задачи, категории, фокус, прогресс, аккаунт и публичные страницы.
- API 1.5: `/me/bootstrap`, `/me/today`, профиль с часовым поясом, сохраненные состояния фокуса и перерывов, серверные дневные награды. Публичного `PATCH /me/stats` нет.
- Транзакции действий над задачами, наград и достижений; идемпотентные команды с сохранением успешного ответа. Это механизм `api_operations`, отдельный от создания платежа.
- Подтверждение YooKassa через API провайдера; атомарное обновление платежа и выдача бессрочного Premium.
- HTTP-метрики Prometheus и middleware запросов; Prometheus и Grafana включены в deployment Compose. Есть сценарий `scripts/loadtest`.
- CI: сборка, модульные и браузерные тесты frontend; backend с PostgreSQL-интеграцией, `-race` и порогом покрытия 80%. Отдельные Go-сервисы тестируются своими заданиями.

## Статус замечаний прежнего аудита

Идентификаторы D1–D16 сохранены для сопоставления со старым документом. Положительный статус означает наличие исправления в коде, а не проверку реальной оплаты или доставки писем.

| ID | Текущий статус | Основание и оставшаяся работа |
|---|---|---|
| D1 | Исправлено | Webhook проверяет `verifiedPayment == nil` до чтения статуса. |
| D2 | Исправлено | Платежный sync использует `CompletePaymentAndGrantPremium`; ошибка записи не выдается за успех. |
| D3 | Исправлено для текущего тарифа | Статус платежа и `is_premium = true` записываются одной транзакцией. Повторная выдача бессрочного boolean-флага не продлевает срок и не списывает деньги. Это не журнал дедупликации событий провайдера. |
| D4 | Частично | Backend передает клиентский `Idempotency-Key` в YooKassa, иначе создает UUID. Клиент в `Account.tsx` вызывает `/payments/create` без устойчивого ключа. Нужно сохранять ключ одной попытки оплаты на повторы; создание нескольких платежей само по себе не доказывает двойное списание. |
| D5 | Частично | Ошибка сохранения платежа теперь возвращает 500. Внешний платеж к этому моменту уже может существовать: требуется восстановление после сбоя между YooKassa и PostgreSQL. |
| D6 | Открыто | `backend/clients/activitylogger/activitylogger.go`: отдельная горутина на событие, без ограниченной очереди и надежного повтора. Ошибки логируются, доставка best-effort. |
| D7 | Частично закрыто | Индивидуальные напоминания используют аренду с fencing token и SKIP LOCKED, пять попыток и журнал. SMTP и БД не атомарны: повтор после принятия письма до записи успеха остается возможен. |
| D8 | Исправлено | Общие интервалы удалены из email-конфигурации и scheduler; интервалы задаются пользователем на каждом напоминании. |
| D9 | Исправлено | Scheduler передает фактический offset_minutes в отправку; для старых абсолютных исключений интервал не задан (передается 0). |
| D10 | Исправлено | Email webhook сравнивает секрет через `subtle.ConstantTimeCompare`. |
| D11 | Частично | Backend имеет `ReadTimeout`, `ReadHeaderTimeout`, `IdleTimeout`; `WriteTimeout` не задан. HTTP-сервер email не задает таймауты. |
| D12 | Открыто | gRPC-соединение activity-logger не сохраняется для явного закрытия клиентом. Это пробел управления ресурсами, а не доказанная утечка между перезапусками процесса. |
| D13 | Исправлено | Цикл очистки токенов ограничен общим контекстом на 30 секунд для двух DELETE. |
| D14 | Технический долг | Внешние ключи используют смесь INTEGER/BIGINT. PostgreSQL допускает эти связи; это не подтвержденная ошибка выполнения. Унифицировать при планировании схемы. |
| D15 | Открыто | `.golangci.yml` существует, но CI не запускает golangci-lint. Сначала проверить совместимость конфигурации с выбранной версией линтера. |
| D16 | Требует эксплуатационной проверки | Goose запускается из backend при старте. Проверить блокировки используемой версии и конкурентный rollout; не считать гонку доказанной только по месту вызова. Рассмотреть отдельный шаг миграций. |

Основные файлы платежного пути: `backend/internal/http-server/handlers/payments/{create,sync,webhook}/` и `backend/internal/storage/postgres/payment.go`. Покрытие и команды проверки: [BACKEND-TESTING.md](BACKEND-TESTING.md).

## Ближайшие работы

1. **Локальная изоляция баз.** В `dev.ps1` порты PostgreSQL и MongoDB публикуются без IP-ограничения; PostgreSQL использует демонстрационные учетные данные. Ограничить публикацию loopback и обновить инструкции. Доступность из внешней сети зависит также от сети и firewall; она отдельно не проверена.
2. **Надежность оплаты.** Закрыть остатки D4/D5: устойчивая попытка создания, повтор с тем же ключом, восстановление внешнего платежа после ошибки БД. Проверить отключение сети и возврат провайдера в тестовом режиме. Сумма `49.00 RUB` пока задана в обработчике.
3. **Доставка напоминаний.** Конкурентный захват, ограниченные повторы и журнал реализованы в `00021`; провести реальную SMTP-проверку перед выпуском. Транзакция PostgreSQL не может атомарно включить SMTP: окно повтора после фактической отправки остается и должно быть явно описано.
4. **Журнал активности.** Ограничить параллелизм, добавить управляемое завершение и закрытие соединения. Если потеря событий недопустима — проектировать transactional outbox и дедупликацию, а не обещать надежность текущей best-effort отправки.
5. **Серверный магазин.** Серверный кошелёк, покупки, личные награды, палитры, звуки и бустер двойного XP реализованы. Новый баланс — 50 монет, импортируются награды и настройки. Дальше: расширенная история и настройка экономики; случайные сундуки остаются отключены.
6. **Эксплуатация.** Таймауты email-сервера, ограниченный shutdown вместо `context.Background()`, обработка ошибки сервера без `log.Fatalf` в горутине; далее статический анализ и политика хранения `api_operations`.

## Что еще нужно проверить

- Согласованность заголовка «Сегодня», отображения сроков и группировки около полуночи при разных поясах браузера и профиля. Прежнее наблюдение расхождения не считается подтвержденным актуальным багом: текущий заголовок использует пояс профиля.
- Полный 25-минутный Pomodoro, автоматическое завершение, восстановительный перерыв 5/15 минут и ошибка сети на завершении. Короткий ручной проход подтвердил запуск с 25:00, дополнительный перерыв, его восстановление после перезагрузки и возврат к работе.
- Реальные подтверждение email, отправку напоминаний, оплату и возврат после нее. Тесты с фикстурами и транспортными заглушками не заменяют эту проверку.
- Полный проход обеих тем и клавиатуры. Ручная проверка темной темы на 360/768/1440 px была ограниченным проходом, а не полной приемкой.
- Результат `-race` в актуальном CI. Последний локальный полный backend-прогон дал 82,77% покрытия (15.10.2026); локально проверка гонок не выполнялась из-за отсутствия C-компилятора. Дата и результат CI должны подтверждаться конкретным запуском.

## Дальнейшие возможности

Это предложения, а не выявленные дефекты и не обязательства по срокам:

- Бизнес-метрики, метрики пула `database/sql`, нагрузочный baseline с p95/p99 и ошибками, защищенное профилирование. HTTP-метрики и инфраструктура мониторинга уже существуют; наличие сценария нагрузки не подтверждает конкретную производительность.
- Разделение liveness/readiness с явным определением критичных зависимостей. Нельзя автоматически делать SMTP и журнал обязательными для готовности всего API.
- SSE для обновления данных между вкладками и устройствами. В текущем клиенте Today опрашивается раз в 30 секунд, состояние фокуса — раз в 15 секунд; инфраструктуру межрепличной доставки выбирать после определения требований.
- Курсоры Today для стабильного снимка между страницами; сейчас согласованность обеспечивается в пределах одного ответа.
- Синхронизация темы, звука и оформления через профиль.
- Проверки зависимостей, секретов и образов в CI с разбором результатов. Само уведомление сканера не является подтверждением эксплуатации или действительности секрета.

При изменении поведения сначала обновлять реализацию и проверки, затем OpenAPI, README и этот список. Не переносить старые номера строк и оценки трудоемкости как актуальные доказательства.
