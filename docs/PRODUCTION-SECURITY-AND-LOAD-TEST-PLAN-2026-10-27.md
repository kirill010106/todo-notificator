# План проверки безопасности и производительности

Дата подготовки: 27 октября 2026 года.

Этот документ задаёт порядок проверки ToDo Notificator. Он не подтверждает состояние production и не является разрешением на активное тестирование внешних адресов.

## Границы

- Сначала выполнить пассивную проверку исходников, истории Git, шаблонов конфигурации и опубликованных клиенту материалов. Не выводить значения секретов в отчёт, терминал, чат или CI-артефакты.
- Нагрузочные сценарии выполнять в изолированном тестовом окружении с отдельными PostgreSQL и MongoDB, синтетическими данными и отключёнными реальными SMTP и платёжным провайдером.
- В production ограничиться согласованными пассивными проверками и обычными проверками доступности. Нагрузочный прогон на рабочем сервере не входит в этот план: инструкции репозитория запрещают запускать нагрузку на production в рамках проверки кода.
- Перед любым активным сетевым тестом зафиксировать письменно владельца, список разрешённых хостов и адресов, окно, максимальную частоту запросов, дежурного оператора и условия немедленной остановки. Не включать сторонние сервисы, если их владелец отдельно не разрешил проверку.

## Что уже известно о проекте

- Основные компоненты: HTTP API на Go, PostgreSQL, activity-logger с gRPC и MongoDB, email-worker, frontend за Traefik. YooKassa подключается отдельно.
- Backend предоставляет Prometheus-метрики на отдельном порту `9091`; в production Prometheus и Grafana привязаны к loopback сервера. Для просмотра с рабочей станции документация рекомендует SSH-туннель.
- Текущий middleware собирает HTTP-счётчики и длительность запросов; backend также экспортирует число открытых, занятых и простаивающих соединений SQL-пула, число ожиданий соединения и суммарное время ожидания. Эти метрики не дают готового полного бизнес-профиля, а подтверждённого production baseline нет.
- `scripts/loadtest/main.go` — сценарий с изменением данных: каждый поток создаёт пользователя, выполняет вход, создаёт три задачи и читает список задач в цикле до окончания времени. Ограничителя запросов и постепенного увеличения нагрузки нет; новые записи не удаляются. Регистрация сохраняет письмо подтверждения в PostgreSQL outbox. Скрипт предназначен только для тестового окружения из README и до доработки нельзя направлять его на production.

## Этап 1. Пассивная проверка утечек

Проверить в локальной копии и без печати найденных значений:

1. Текущие отслеживаемые файлы и доступную историю Git на пароли, ключи, токены, DSN, приватные ключи и production-дампы. Игнорируемые `.env` не открывать и не копировать; проверить только наличие и правила исключения файлов.
2. `.env.example`, `.env.production.example`, Compose, Ansible и CI: разделение секретов по сервисам, отсутствие секретов во frontend build args, Docker build context и логах.
3. Публичные артефакты frontend: встроенные `VITE_*`, source maps, заголовки и ответы на ошибки. Серверные значения не должны попадать в клиентскую сборку.
4. HTTP-ответы, access/error-логи и метрики на предмет паролей, токенов, ссылок сброса/подтверждения, email-содержимого, SQL-данных и идентификаторов, которые не нужны наблюдаемости. Для меток HTTP-метрик проверить, что используются шаблоны маршрутов, а резервный путь не создаёт метки с чувствительными или высококардинальными значениями.
5. Границы доступа к административным панелям и метрикам: сверить фактические listeners, reverse proxy и firewall с конфигурацией. Не считать состояние production подтверждённым только по исходникам.

Отчёт должен содержать путь или компонент, тип возможной утечки, способ безопасного воспроизведения, условия и исправление. Секретные фрагменты заменять маркером `[REDACTED]`. Если подтверждён опубликованный действующий секрет, сообщить только его владельцу безопасным каналом и отдельно согласовать ротацию; не проверять его пригодность реальным входом.

## Этап 2. Подготовка тестовой среды

- Использовать изолированный стенд с конфигурацией, близкой к production, но с отдельными БД, ключами и доменами. Не подключать production DB, очередь, email, YooKassa или пользовательские данные.
- Для email использовать локальный sink/mock; платежи и webhooks заглушить. Тестовые адреса и записи должны быть явно маркированы.
- Зафиксировать версии образов, схему БД, лимиты контейнеров, конфигурацию reverse proxy, сетевые ограничения и состав мониторинга. Если стенд заметно отличается от production, перечислить это в отчёте.
- До прогона проверить резервное копирование стенда и процедуру остановки генератора. Установить максимальную длительность, предел параллельности и скорость запросов; сначала выполнить короткий smoke-прогон.
- Улучшить или заменить текущий генератор: поддержать pacing/rate limit и постепенный ramp-up, контролируемое число пользователей, таймауты, ограничение ошибок, случайные паузы, отчёт по статусам и задержкам, а также отдельный идентификатор тестовых данных и безопасную очистку только в тестовой БД.

## Этап 3. Нагрузочный прогон на стенде

1. Снять baseline без генератора: CPU, память, диск, сеть, контейнерные рестарты, PostgreSQL connections/locks/slow queries, состояние MongoDB и email-outbox.
2. Выполнить smoke-проверку небольшим числом тестовых пользователей.
3. Увеличивать нагрузку ступенями с постоянной скоростью на каждой ступени. Конкретные значения параллельности и RPS выбрать после согласования ожидаемого трафика и лимитов стенда; универсальные числа не подставлять.
4. Разделить сценарии чтения и записи. Включать реальные API-потоки только с синтетическими аккаунтами; отдельно измерять регистрацию и связанные с ней outbox-записи. Не включать платежи и реальную доставку писем.
5. После нахождения целевого уровня выполнить короткий soak-прогон для проверки накопления очередей, соединений и памяти. Проводить его только пока показатели остаются в заранее заданных пределах.
6. Сопоставить достигнутый RPS, p50/p95/p99, долю 2xx/4xx/5xx и таймаутов, использование CPU/RAM, соединения/ожидания БД, глубину очередей и рестарты. Разделять ожидаемые ответы rate limit `429` и ошибки приложения.

## Наблюдение и остановка

До начала прогона записать численные пороги из SLO и текущих лимитов стенда. Немедленно остановить генератор при любом из условий:

- ошибки или задержки превышают согласованные пороги;
- readiness/health перестаёт проходить или растёт число 5xx;
- БД исчерпывает соединения, появляются длительные блокировки, растёт очередь запросов или резко увеличивается число медленных запросов;
- очередь email/outbox растёт либо неожиданно появляется внешняя доставка;
- контейнеры перезапускаются, память или диск достигают заданного предела;
- нагрузка затрагивает нецелевой адрес или реальные данные.

Снимать метрики через уже настроенные Prometheus/Grafana, если они доступны на стенде. Исходники подтверждают HTTP-счётчики и длительность, а также базовые метрики SQL-пула; метрики PostgreSQL locks/slow queries, контейнеров и бизнес-очередей отдельно не подтверждены. Недостающие показатели получать из наблюдаемости стенда; не открывать Prometheus/Grafana наружу только ради теста.

## Production-проверки

В рамках текущей задачи production можно проверять только пассивно: читать конфигурацию через одобренный доступ, проверять публикацию чувствительных страниц и выполнять заранее согласованный низкочастотный smoke-check доступности. Для любых проверок с изменением состояния нужны отдельные тестовые аккаунты, согласованный план очистки и отдельное окно. Регистрацию, создание записей, платежи, сброс пароля, email-trigger и нагрузочный профиль к production не применять.

## Итоговый отчёт

Для каждого результата указать дату, проверенный commit/image tag, точную среду и её отличия от production, сценарий, длительность, ступени нагрузки, измеренные значения, ошибки и ограничения вывода. Отдельно перечислить неподтверждённые интеграции и утечки, требующие действий владельца. Секреты, пользовательские данные, токены и полные тела запросов в отчёт не включать.
