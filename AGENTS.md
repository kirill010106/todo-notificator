# Инструкции для работы с ToDo Notificator

## Область действия и границы задачи

- Инструкции действуют для всего репозитория. Перед работой проверь `git status` и более узкие `AGENTS.md`; сохраняй чужие изменения.
- Выполняй именно запрошенную работу. В задачах аудита и планирования меняй только документацию и материалы проверки. Исправлять приложение, зависимости, миграции и инфраструктуру можно, когда это входит в запрос пользователя.
- Не запускай деплой, реальные платежи, отправку писем или нагрузку на рабочий сервер в рамках проверки кода. Используй локальные заглушки и одноразовые тестовые данные.
- Не выводи секреты из `.env`, токены, пароли, DSN и production-данные. Для примеров используй вымышленные значения.

## Как ориентироваться в проекте

- Начни с `README.md`, `.github/CODEBASE.md` и документации затронутого потока. Сверяй описание с текущими исходниками: документация может отставать.
- `backend/`: Go, chi, PostgreSQL, HTTP API `/api/v1`. Реальные маршруты определяются в `backend/internal/http-server/router/router.go`.
- `frontend/`: React, TypeScript, Vite, TanStack Query. API и управление токенами находятся в `frontend/src/lib/api.ts`.
- `activity-logger/`: gRPC и MongoDB. `backend/clients/activitylogger/` отправляет события асинхронно, best-effort.
- `notifiers/email/`: отдельный Go-модуль, SMTP, webhook и workers; `notifiers/shared/` входит в модуль `notifiers`.
- `go.work` объединяет пять модулей. Корневой `go test ./...` не заменяет проверки каждого модуля.
- HTTP-контракт: `docs/openapi.yaml`; правила предметной области: `docs/BUSINESS-LOGIC.md`; окружение: `docs/ENVIRONMENT.md`; выпуск: `docs/DEPLOYMENT.md`.

## Проверка замечаний и уязвимостей

- Проверяй текущий HEAD, а не только строки из старого отчёта. Для каждого замечания проследи подключённый маршрут, middleware, реализацию хранилища и конфигурацию запуска.
- Не объявляй дефектом код, который не вызывается в рассматриваемом сценарии. Например, публичная регистрация сейчас использует `account.Handler.Register`, а не старый `handlers/auth/register.New`.
- Оставляй в списке исправлений подтверждённые дефекты с конкретным сценарием и последствием. Указывай необходимые условия: тариф, размер истории, порядок ответов, доверенный IP, включённый деплой или доступ к БД.
- Различай исполнение реального обработчика с заглушкой, проверку SQL через sqlmock, проверку конфигурации и интеграцию с настоящей БД. Заглушка не подтверждает поведение PostgreSQL, MongoDB или платёжного провайдера целиком.
- Для гонок проверяй оба порядка завершения запросов. Для транзакций проверяй откат на ошибке промежуточного шага. Для курсоров проверяй ошибку следующей порции и ошибку декодирования.
- Отсутствие лимита само по себе не доказывает падение сервера. Показывай принятую величину и выполненную работу; не утверждай OOM, захват аккаунта или обход IP-фильтра без соответствующего доказательства.
- Проверяй компенсирующие меры: лимиты прокси, таймауты, rate limit, gRPC-лимиты и доступность сервиса извне. Не приписывай production-настройки, которые не были прочитаны.
- Приоритет определяется последствием и условиями: P1 — высокий риск компрометации/серьёзного отказа при указанной предпосылке; P2 — существенная ошибка доступности или корректности; P3 — ограниченный эксплуатационный риск. Всегда объясняй условность риска.
- В отчёте сохраняй исходный номер замечания, актуальное место в коде, способ проверки, наблюдаемый результат и рекомендуемое исправление. Исключённые замечания объясняй отдельно от рабочего списка.
- Повторная проверка исходной таблицы от 20.10.2026: `docs/SECURITY-RECHECK-2026-10-20.md`. Это датированный результат, а не вечная истина о состоянии проекта.

## Правила для будущих исправлений

- Сохраняй проверку владельца данных и актуальных прав аккаунта в БД. Не полагайся только на Premium/is_verified из старого JWT.
- Связанные изменения аккаунта, токенов и заданий доставки выполняй атомарно. Соблюдай существующий порядок блокировок: пользователь перед токенами.
- Сохраняй идемпотентность команд, платежей и начисления наград; не расширяй допустимые переходы терминальных состояний без проверки контракта.
- Ограничивай тело до JSON-декодирования и пагинацию до запроса к хранилищу. Передавай отмену входящего контекста в зависимые операции.
- Не перенумеровывай и не переписывай применённые миграции; изменения схемы оформляй новой миграцией. Не редактируй вручную сгенерированные protobuf-файлы и mocks.
- При изменении API согласуй обработчики, OpenAPI и frontend. Учитывай общий `localStorage` нескольких вкладок, выход и смену аккаунта во время запросов.
- Не заявляй надёжную доставку для best-effort журнала. Изменение гарантий доставки требует отдельного решения и проверок.

## Проверки

- Запускай проверки, относящиеся к изменению. Документационные правки не требуют полного CI. Для исправления дефекта добавляй проверку его последствия, если существующие тесты его не покрывают.
- Быстрые Go-проверки: `go test -p 1 ./... -count=1` из соответствующего модуля. У `activity-logger/cmd` существующий `TestServerIntegration` требует Docker даже без build tag.
- Полный backend-набор с PostgreSQL, `-race` и порогом покрытия 80% описан в `docs/BACKEND-TESTING.md`. Нельзя подменять его процентом только модульных тестов или объявлять пройденным без Docker.
- Frontend: из `frontend/` запускай `npm test`, `npm run build`; при изменениях пользовательских потоков — `npm run test:e2e` с установленным Chromium. API-фикстуры Playwright не проверяют реальные SMTP и платежи.
- Для скриптов выпуска используй соответствующие `python -m unittest discover -s scripts -p 'test_deploy_release*.py' -v` и `python -m unittest discover -s scripts -p 'test_release_config.py' -v`; контейнерная часть имеет отдельные требования.
- Если окружение мешает проверке, укажи конкретное ограничение и что всё же проверено. Не выдавай пропущенный тест за успешный.
- В итоговом ответе перечисли созданные/изменённые документы или код, результаты проверок и существенные ограничения. Не создавай коммит или PR без запроса пользователя.
